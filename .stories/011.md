# Story 011: The popover ships its six fonts as .woff2 only, loads the latin-ext faces only for text that needs them, and builds for Safari 15 without the modulepreload polyfill

## Symptom

`src/main.tsx:5-10` loads the fonts through six fontsource CSS files:
`@fontsource/silkscreen/latin-400.css` and `latin-700.css`, and
`@fontsource/sometype-mono/latin-400.css`, `latin-ext-400.css`,
`latin-600.css` and `latin-ext-600.css`. Each file declares one `@font-face`.
Its `src` lists the `.woff2` file, then the `.woff` file, and none of the six
declares a `unicode-range`. The result:

- **Twelve font files are shipped and only six are used.** Vite emits both
  files for every face. The app's webview is WKWebView on macOS 12 or later
  (`src-tauri/tauri.conf.json:50`). It supports woff2 and takes the first
  source it supports, so the six `.woff` files are never loaded. They are
  still built into the app: the shell embeds `dist/` at compile time
  (`scripts/check-macos-shell.sh:12-13`, `src-tauri/tauri.conf.json:9-10`).
- **Both Sometype Mono subsets claim every code point.** With no
  `unicode-range`, the latin-ext faces are fetched even for text that has no
  latin-ext character.
- **A stale comment.** `src/main.tsx:4` says "Latin subsets only", but lines 8
  and 10 import the latin-ext subset.

`vite.config.ts:6-14` sets no `build` options:

- **The target is above the oldest webview.** Vite 8.3.5's default target is
  `"baseline-widely-available"`
  (`node_modules/vite/dist/node/chunks/node.js:34598`). Vite expands it to a
  list that includes `safari16.4`
  (`node_modules/vite/dist/node/chunks/node.js:731-737`,
  `node_modules/vite/dist/node/chunks/node.js:34653`). That is newer than
  Safari 15, which macOS 12.0 ships.
- **The modulepreload polyfill is bundled for nothing.** The default
  `modulePreload` has `polyfill: true`. `index.html:10` loads a module
  script without `async`, so Vite imports the polyfill into the entry
  (`node_modules/vite/dist/node/chunks/node.js:31954`,
  `node_modules/vite/dist/node/chunks/node.js:32032`). There is no dynamic
  `import()` in `src/` outside the tests, so the build has one chunk and
  nothing to preload.

## Evidence

I read the code at `epic/quality` (a518b28). I read the fontsource and Vite
files in an install of the versions `package-lock.json` locks:
`@fontsource/silkscreen` 5.3.0, `@fontsource/sometype-mono` 5.3.0, Vite
8.3.5. Nothing was built, run or measured. The premise holds as the request
states it.

### The package CSS today

`@fontsource/sometype-mono/latin-ext-400.css`, in full:

```css
/* sometype-mono-latin-ext-400-normal */
@font-face {
  font-family: 'Sometype Mono';
  font-style: normal;
  font-display: swap;
  font-weight: 400;
  src: url(./files/sometype-mono-latin-ext-400-normal.woff2) format('woff2'), url(./files/sometype-mono-latin-ext-400-normal.woff) format('woff');
}
```

The other five files differ only in family, weight and file name. Every one
has `font-style: normal` and `font-display: swap`.

### The package's own ranges

The package's whole-weight files, `@fontsource/sometype-mono/400.css` and
`600.css`, give each subset face a `unicode-range`. The values are the
entries of `@fontsource/sometype-mono/unicode.json`:

- `latin`: `U+0000-00FF,U+0131,U+0152-0153,U+02BB-02BC,U+02C6,U+02DA,U+02DC,U+0304,U+0308,U+0329,U+2000-206F,U+20AC,U+2122,U+2191,U+2193,U+2212,U+2215,U+FEFF,U+FFFD`
- `latin-ext`: `U+0100-02BA,U+02BD-02C5,U+02C7-02CC,U+02CE-02D7,U+02DD-02FF,U+0304,U+0308,U+0329,U+1D00-1DBF,U+1E00-1E9F,U+1EF2-1EFF,U+2020,U+20A0-20AB,U+20AD-20C0,U+2113,U+2C60-2C7F,U+A720-A7FF`

### The package files and the faces in use

- **Package paths.** Both packages' `exports` map `./files/*.woff2` to
  `./files/*.woff2`. So `@fontsource/<pkg>/files/<name>.woff2` names
  `node_modules/@fontsource/<pkg>/files/<name>.woff2`. All six `.woff2` files
  named in AC1 exist there.
- **The faces the popover uses.** `src/styles.css:14-15` define `--pixel`
  ("Silkscreen") and `--mono` ("Sometype Mono"). Silkscreen is set at 700
  (`src/styles.css:59`) and 400 (`src/styles.css:290`). Sometype Mono is set
  at 400 (`src/styles.css:18`) and 600 (`src/styles.css:163`). The six faces
  today cover exactly these weights. This story keeps the same six.

### How Vite handles a CSS `url()`

Vite resolves the url with its module resolver, trying a relative path first
(`preferRelative: true`,
`node_modules/vite/dist/node/chunks/node.js:29933-29937`). It then emits the
file as a hashed asset.

A url that Vite cannot resolve is left as written, and the build only warns
(`node_modules/vite/dist/node/chunks/node.js:29989-29990`). The build does
not fail, so a wrong path would ship a font that 404s at runtime. That is why
AC1 checks that every url names a file that exists.

### The measurement in the request (not re-measured)

The coordinator's bundle analysis measured this on `develop`:

- dist ships each of the six faces twice: as `.woff2` (49,132 B together)
  and as `.woff` (54,148 B together);
- the JS is 243.7 KB, and react-dom is about 207 KB of that.

An older baseline build log in the repo lists the same twelve font files
(`.review/004/round-1/baseline/build.log:11-22`).

### Decisions already made by the coordinator (delegated by the human)

- **React stays.** A measured preact/compat swap was rejected. preact/compat
  lacks `useEffectEvent` (`src/components/useCardKeys.ts:1`), and the tests
  use `@testing-library/react`. Apart from the polyfill, this story does not
  make the JS smaller.
- **Silkscreen stays latin only.** It draws only the app's own upper-case
  English words.
- **Sometype Mono keeps latin-ext.** Decoded network names and contact names
  can be Turkish, Polish and so on.

### `build.target` is a compatibility fix, not a size cut

`build.target: ["safari15"]` makes the build aim at the oldest webview the
app supports. A lower target may add bytes to the JS or the CSS. Nobody knows
whether today's bundle contains syntax that Safari 15 cannot parse.

### A constraint on the test

- **`node:fs` does not type-check.** `npm run build` runs `tsc --noEmit`
  (`package.json:8`) over `src` (`tsconfig.json:16`), with
  `types: ["vite/client"]` only (`tsconfig.json:14`). `package-lock.json` has
  no `@types/node`, so a test that imports `node:fs` fails the type check.
- **What existing tests use.** They read files with Vite's `?raw`
  (`src/__tests__/tauriSecurity.test.ts:6-7`) and list files with
  `import.meta.glob` (`src/__tests__/tauriSecurity.test.ts:66`).
  `import.meta.glob` skips `node_modules` unless it is given
  `exhaustive: true` (`node_modules/vite/dist/node/chunks/node.js:27952`).
- How the test proves that a font file exists is the builder's choice.

## Acceptance criteria

The instrument for every AC is one new vitest file under `src/__tests__/`.

**AC1 — `src/fonts.css` holds six @font-face rules and nothing else, one for each face the popover uses today. Each loads one .woff2 file from its @fontsource package, and each Sometype Mono face carries the package's unicode-range for its subset.**
Instrument: the test reads `src/fonts.css` as text and removes its `/* */`
comments before checking (a) to (d).

(a) **Six rules, nothing else.** The file holds exactly six `@font-face`
rules. It holds no `@import`, no other at-rule and no style rule.

(b) **The six faces.** Each rule declares `font-style: normal` and
`font-display: swap`, as the package CSS does. Its family (quotes removed),
its `font-weight` and the file its url resolves to (c) form one row of this
list, and each row is used exactly once:
- Silkscreen, 400, `node_modules/@fontsource/silkscreen/files/silkscreen-latin-400-normal.woff2`
- Silkscreen, 700, `node_modules/@fontsource/silkscreen/files/silkscreen-latin-700-normal.woff2`
- Sometype Mono, 400, `node_modules/@fontsource/sometype-mono/files/sometype-mono-latin-400-normal.woff2`
- Sometype Mono, 400, `node_modules/@fontsource/sometype-mono/files/sometype-mono-latin-ext-400-normal.woff2`
- Sometype Mono, 600, `node_modules/@fontsource/sometype-mono/files/sometype-mono-latin-600-normal.woff2`
- Sometype Mono, 600, `node_modules/@fontsource/sometype-mono/files/sometype-mono-latin-ext-600-normal.woff2`

(c) **One woff2 url per face, and the file exists.** Each `src` is exactly
one `url(...)` followed by `format("woff2")` or `format('woff2')`, and
nothing else. The test resolves the url:
- a url that starts with `@fontsource/` resolves to `node_modules/` followed
  by the url;
- a url that starts with `../node_modules/@fontsource/` resolves to that path
  taken from `src/`;
- any other form fails.

The resolved file must exist.

(d) **Unicode ranges.**
- The two Sometype Mono faces whose file is a `latin-ext` file declare a
  `unicode-range` equal to the `latin-ext` entry of
  `@fontsource/sometype-mono/unicode.json`.
- The two whose file is a `latin` file declare a range equal to its `latin`
  entry.
- The test compares with whitespace removed. It reads the expected values
  from the package file or holds them as literals copied from it.
- The two Silkscreen faces declare no `unicode-range`. The package's
  `latin-400.css` and `latin-700.css` declare none today.

On the base, `src/fonts.css` does not exist and the test fails.

## Known weakness of the instrument

- **Text, not glyphs.** The tests read three files as text. They check
  families and weights by name. Fonts look the same as before only if those
  match, and that is something a person sees in the app.
  - The request says the macOS CI build would also show it. It would not.
    The macOS workflow builds the app (`.github/workflows/macos.yml:39`) but
    never opens the popover. It proves the build works, not how the text
    looks.
- **The test's resolution, not Vite's.** AC1 (c) resolves each url by its
  own rule.
  - That Vite resolves `@fontsource/…/files/….woff2` the same way, through
    the package's `exports`, comes from reading Vite's source. It was not
    observed.
  - If Vite cannot resolve a url, it only warns (Evidence). The build stays
    green, dist gets no font file, and the font 404s at runtime.
  - Only the build's asset list shows this, and no test asserts it. The
    builder lists `dist/assets` from its own `npm run build`, before and
    after, in the commit message.
- **dist size is not asserted.** The harness builds after the tests run. The
  byte counts in Evidence are the coordinator's, measured on `develop`. The lower
  target may add bytes.
- **unicode-range.** AC1 (d) proves the declared ranges equal the package's.
  - It does not show WebKit skipping the latin-ext file when no character
    needs it. That is the CSS Fonts matching rule, and it was not observed
    here. Human verification checks it.
  - That each subset file holds the glyphs its range names is fontsource's
    claim. The test does not check it.
- **Safari 15 is never run.** AC3 proves the config value. It does not prove
  that the output parses in Safari 15.
  - Nothing here runs WebKit 15. CI uses `macos-14`
    (`.github/workflows/macos.yml:19`).
  - Whether Vite 8's transpiler accepts `safari15` shows first in the
    builder's own build, where a failure turns the baseline red.
- **AC2 covers a fixed set of files.** It sees `index.html` and `src/`
  outside the tests. Font CSS injected some other way, for example by a
  plugin added in `vite.config.ts`, would not show up.
- **Comments.** AC1 ignores comments in `src/fonts.css`. A `.woff` url inside
  a comment passes, and rightly so: a comment loads nothing. AC2 counts
  comments.
