# Story 004: Find every QR code on screen with one action, without dragging a box

## Symptom

There is no way to find several codes without dragging a box around them. A
scan is always interactive: `src-tauri/src/scan.rs:21` `spawn()` →
`capture_and_decode()` (`src-tauri/src/scan.rs:48-73`) → `qr_core::run_scan`
(`core/src/scan.rs:41-75`) with a `Capturer` (`core/src/scan.rs:34-37`). The
only `Capturer` on macOS is `Screencapture`
(`src-tauri/src/platform/macos.rs:41-61`), which runs
`/usr/sbin/screencapture -i -x <file>` (`src-tauri/src/platform/macos.rs:47-49`):
the system crosshair, one region, one image. The page starts it only through
`ipc.startScan` (`src/lib/ipc.ts:16`) from the Scan button
(`src/App.tsx:98-100`) or "Scan again" (`src/App.tsx:74-77`); the tray menu
has only "Scan QR Code" and "Quit" (`src-tauri/src/tray.rs:12-16`); the
global shortcut starts the same drag scan (`src-tauri/src/lib.rs:17-19`).

The human wants one action that captures every connected display at once,
decodes each image, and shows the codes it found as the usual cards.

## Evidence

Verified by reading the files on `epic/find-all` (it is at 7e940a7, the same
commit as `develop`; the epic has no commits of its own yet). Nothing was
built or run.

  and `site/` for "find all", "find_all", "findAll", "displays" and "whole

  - one scan at a time: `ScanState` (`src-tauri/src/scan.rs:26-32`);
  - permission checked before anything is hidden
    (`src-tauri/src/scan.rs:49-51`), and again in core before capture
    (`core/src/scan.rs:47-49`);
  - `scan://started`, then the popover hidden, then a 150 ms settle before
    capture (`src-tauri/src/scan.rs:59-63`, `src-tauri/src/scan.rs:13`);
  - the screenshot in a temp dir under the cache dir, removed when
    `run_scan` returns (`core/src/scan.rs:50`);
  - `scan://result` with a `ScanOutcome` (`src-tauri/src/scan.rs:41`,

- The page already renders one card per code in a `found` outcome
  (`src/App.tsx:125-135`), keyed by `code.text` (`src/App.tsx:128`), and

  duplicate React key and be dismissed together. The decoder dedups within

- The page's secondary button style is `className="ghost"`: an outlined
  button using the base `button` rule (`src/styles.css:73-82`), as on "Try

  image per display, the main display first. This is the coordinator's
  decision, matching screencapture(1). Also not verified: which CoreGraphics
  call the builder uses to count displays; `macos.rs` already links
  CoreGraphics (`src-tauri/src/platform/macos.rs:6-10`).

**The page must learn which kind of scan ran (coordinator's choice, under
the human's delegation).** Today `scan://started` carries no payload
(`src/lib/ipc.ts:31-40`), and the outcome is the same `ScanOutcome`, so the
not-found notice "No QR code in that area. Try a box around the whole
code…" (`src/App.tsx:110`) would show after a find-all and tell the user to
fix a box they never drew. So:
- `scan://started` carries the scope as its payload: the string `"area"`
  for the drag scan, `"screen"` for a find-all, whoever started it (button,
  tray, shortcut). `ipc.onScan` passes it to its `started` handler.
- `src/lib/scanState.ts` keeps the scope of the running scan, and the
  not-found view knows it. After a `"screen"` scan the notice says the
  screen was searched and nothing was found; the builder writes the
  sentence. After an `"area"` scan it stays exactly as it is.
- The scanning prompt "Select the code…" (`src/App.tsx:95`) is left as it
  is: the popover is hidden while a find-all captures.

## Known weakness of the instrument

- **No Rust is an AC instrument.** The harness mutates only what vitest
  sees. The core behaviour (1a–h) is held by the builder's cargo tests in
  the baseline. A merge or cleanup bug that those tests do not exercise
  would pass the harness. The reviewer has to read them against 1a–h.
- **The macOS part was never run.** It is checked only by
  `scripts/check-macos-shell.sh` (it type-checks and lints as macOS
  compiles, and never links or runs), by macOS CI on a push to `develop` or
  a PR (`.github/workflows/macos.yml:7-11`), and by a person on a Mac. None
  of these has been observed:
  - that `screencapture -x` with N files writes one per display, main
    first;
  - that the display count is right with one, two or a mirrored display;
  - that the popover and the closing tray menu are out of the images;
  - that the files are gone from the cache directory on a real Mac.
- **The command name is half-checked.** AC3 pins the string on the page
  side only. The Rust function's name and its `generate_handler!` entry are
  checked by reading. A mismatch is not a compile error: it shows only on a
  Mac, as a "command not found" error card.
- **jsdom does no layout and loads no CSS.** AC1 asserts DOM order and the
  class that selects the outlined rule. Whether the button looks secondary,
  and whether its Silkscreen label fits the 360 px popover on one line, only
  a person sees.
- **The disabled state is checked only on the page.** AC2 checks the page's
  disabled state. What actually prevents overlapping scans from the tray or
  the shortcut is the shared `ScanState` flag (item 3), which no test
  reaches here.
- **AC4 is green on the base.** It guards against regression and shows
  nothing about the new feature.
- **Decoding a whole display is unmeasured.** No one has measured how long
  rxing takes on a full Retina display, or whether it finds small codes
  there. The decoder retries upscaled only when the image is under 600 px on
  its short side (`core/src/decode.rs:30`), so a small code that a tight
  drag box finds may be missed in a full-display image. This is the
  decoder's behaviour, and this story does not change it.
- **The tray item has no test** of any kind beyond compiling.
- **The scope payload is checked on the page only.** AC5 feeds `"screen"`
  and `"area"` to the page's handlers. That Rust emits those exact strings
  with `scan://started` is checked by reading and on a Mac.
