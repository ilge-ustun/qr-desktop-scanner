# Story 010: Link warnings name the right owner after a trailing dot or under a country suffix, and warn on extra mailto recipients and on local destinations

## Symptom

A security review found three gaps in the link warnings in
`src/lib/urlSafety.ts`. I confirmed each one by reading the current file.

1. **The decoy warning names the wrong owner in two cases.** The owner is
   the last two labels of the host. It is the last three when the last two
   are in `TWO_PART_SUFFIXES`, a fixed list of 19 entries
   (`src/lib/urlSafety.ts:35-55`, used at `src/lib/urlSafety.ts:132-135`).
   - **A trailing dot.** For `https://paypal.com.evil.com.` the host keeps
     its dot. Its last label is `""`, so the owner is `com.`. The card's
     headline shows `com.`, and the warning says the address "belongs to
     com.." (`src/lib/urlSafety.ts:141`, `src/lib/urlSafety.ts:143`).
   - **A country suffix not in the list.** For
     `https://paypal.com.evil.co.kr`, `co.kr` is not in the list, so the
     owner is `co.kr` instead of `evil.co.kr`.
2. **A mailto with extra recipients gets no warning.** `assess` returns no
   warnings for every `mailto:` (`src/lib/urlSafety.ts:72-74`). Take
   `mailto:boss@corp.com?bcc=x@evil.com&body=…`. Its headline is
   `boss@corp.com`, everything before the `?` (`src/lib/payload.ts:46`,
   `src/components/ResultCard.tsx:55`). Its tone is ok, so ⌘O opens it
   directly (`src/components/ResultCard.tsx:77`).
3. **Local destinations get no warning of their own.** Only a dotted IPv4
   host or a bracketed IPv6 host gets a caution, `ip-address`
   (`src/lib/urlSafety.ts:60`, `src/lib/urlSafety.ts:118-124`). That warning
   says nothing about the network.
   - `https://localhost/` and `https://printer.local/` get no warning at all.
     Their `http:` forms get only `not-encrypted`.
   - `https://192.168.1.10/` gets the same caution as a public address.

## Evidence

I read the files at `epic/quality` (05cb38a). Nothing was built, run or
measured.

    run this here. AC1 makes the test check it first.
  - `host.split(".")` then ends in `""`, and the slice at
    `src/lib/urlSafety.ts:133-134` gives `com.`.
- **Premise 1b, confirmed by reading.** `src/lib/urlSafety.ts:133` looks
  only in the list. The list has no `kr` entry.
- **The coordinator's rule, delegated by the human.**
  - When the last label is a two-letter country code, and the label before
    it is one of `co`, `com`, `net`, `org`, `ac`, `gov`, `edu`, `or`, `ne`,
    `go`, the two together are the suffix. So the owner of
    `paypal.com.evil.co.kr` is `evil.co.kr`.
  - The existing list stays.
  - The decoy warning keeps its code, severity and message template. Only
    the owner it names, and the `domain` the card shows, change.
- **Found while reading: every entry in today's list already fits the
  rule.** All 19 have a second label from the ten and a two-letter last
  label: `co.uk`, `org.uk`, `ac.uk`, `gov.uk`, `com.au`, `net.au`, `org.au`,
  `co.jp`, `ne.jp`, `or.jp`, `com.br`, `net.br`, `org.br`, `co.nz`, `co.in`,
  `co.za`, `com.mx`, `com.cn`, `com.tr`.
  - So once the rule is in, the list adds no case.
  - The coordinator's intent keeps it, so this story keeps it.
  - No criterion depends on it.
- **The shortener check is unaffected by the rule.**
  - It compares `host` with `SHORTENERS` (`src/lib/urlSafety.ts:125`).
    It runs before the suffix code (`src/lib/urlSafety.ts:132-136`) and
    reads nothing from it.
  - Under the new rule, each of the 13 hosts in `SHORTENERS`
    (`src/lib/urlSafety.ts:18-32`) is still its own owner. In `t.co` and
    `s.id` the label before the two-letter code is `t` or `s`, which is not
    one of the ten.
  - The existing test at `src/__tests__/urlSafety.test.ts:54-57` covers the
    check. No criterion here is about it: no change this story asks for
    could make one go red.
  - The shortener check also reads the host with its trailing dot, so
    `https://bit.ly./x` gets no `shortener` warning today. Dropping the dot
    before that check is allowed but not required, and no criterion tests
    it.
- **Premise 2, confirmed by reading: on the card, ⌘O on a warned link only
  moves focus (story 005).**
  - Any warning makes the tone `warn` or `danger`
    (`src/components/ResultCard.tsx:49-53`).
  - Then ⌘O calls `openAnyway.current?.focus()` instead of `open`
    (`src/components/ResultCard.tsx:77`).
  - The card shows `Open anyway` instead of `Open`
    (`src/components/ResultCard.tsx:110-121`).
  - So a caution on the mailto needs no change outside `src/lib/`, and
    `openable` stays `true`.
  - The message is rendered as text (`src/components/ResultCard.tsx:97`).
  - Warnings are keyed by `code` (`src/components/ResultCard.tsx:93`), so a
    code may appear only once per assessment.
- **Premise 3, confirmed by reading.**
  - `IPV4` matches only a dotted quad (`src/lib/urlSafety.ts:60`).
  - No line in `assess` reads a host name for `localhost` or `.local`.
  - The URL parser rewrites `2130706433` to `127.0.0.1` and
    `[0:0:0:0:0:0:0:1]` to `[::1]`. That is the WHATWG URL Standard's host
    parser. I did not run it here. AC5 makes the test check both first.
- **Rust is unchanged.** `core::url_guard` checks the scheme only
  (`core/src/url_guard.rs:9`). An `Open anyway` on a local link still
  opens it. The coordinator's intent excludes url_guard from this story.
- **No type change reaches the components.** `Warning.code` is a `string`
  (`src/lib/urlSafety.ts:6`), and `Assessment` keeps its shape. So
  `src/components/` needs no edit, and it is denied whole.
- **Story 009 is running on `epic/quality` too.** Its `scope_deny` covers
  `src/lib/*` and this test file, so the two do not overlap.
- **Messages.** The request asks this story to write them, in the voice of
  `src/lib/urlSafety.ts:79-129`: short, plain, what the link does, then
  what to do.
  - `local-address`: `The link goes to this Mac or a device on your local
    network, not a public website.` This mirrors `ip-address`.
  - `extra-recipients`: `The link adds <recipients> to the recipients.
    Check every address before you send it.` It avoids "also", so it still
    reads right for `mailto:?to=…`, which has no address before the `?`.
- **This story's readings.** The writer proposed these; the coordinator
  accepted all five (delegated by the human, 22 Oct 2026).
  1. **The shown domain drops the dot for every host.** Dropping one
     trailing dot applies to the `domain` of a host with no decoy warning
     as well: `https://www.example.com./` shows `www.example.com`.
  2. **A local IP keeps `ip-address`.** It gets both `ip-address` and
     `local-address`. The request says *add* a caution with its own
     message, so the existing one stays.
  3. **Recipients are shown percent-decoded.** `bcc=j%40evil.com` is named
     as `j@evil.com`, so an encoded address cannot hide. A malformed escape
     must not make `assess` throw.
  4. **The trailing dot counts for local names too.** `localhost.` and
     `nas.local.` are local hosts.
  5. **The codes are `extra-recipients` and `local-address`.** Both are
     kebab-case, like the existing codes.

## Known weakness of the instrument

- **These are heuristics, not the Public Suffix List.**
  - A suffix like `com.br` or `co.kr` is covered. An odd one is not:
    - `gob.mx` and `ltd.uk` have a second label outside G.
    - Deeper suffixes such as `k12.ca.us` have more than two labels.
    - Private suffixes such as `github.io` are not covered. The Public
      Suffix List has them for other reasons.
  - "Two-letter country code" is read as any two-letter last label. It is
    not checked against the ISO list.
  - **The rule can also take a suffix where none exists.** A host under a
    domain literally named `co.de` is judged one label short. For
    `paypal.com.co.de` the owner becomes `com.co.de`, and the decoy warning
    the base gives (owner `co.de`) is lost. An attacker would have to own
    `co.de` itself.
  - **An owner whose own first label is in the decoy set is not flagged.**
    `login.secure.com.co.kr` belongs to `com.co.kr`, so its front is
    `login.secure` and it gets no warning. On the base it is warned, as
    belonging to `co.kr`. `com.co.uk` behaves the same today.
- **AC1 tests five country codes.** A change that listed exactly the 50
  tested suffixes instead of writing the rule would pass. The reviewer reads
  the diff for that.
- **Only one trailing dot is handled.** `evil.com..` is not, and it does not
  resolve in DNS anyway.
- **The URL parser is the test environment's.**
  - AC1 and AC5 assert the parsed hostname first. That proves what the URL
    class in vitest's jsdom environment does. I did not check whether that
    class is Node's or jsdom's; both follow the WHATWG URL Standard.
  - In the app, `assess` runs on WKWebView's URL parser. Its handling of
    `2130706433`, `[0:0:0:0:0:0:0:1]` and a trailing dot was not observed.
- **Local hosts are only the listed forms.** These are not covered:
  - `0.0.0.0` (`http://0/`) and `[::]`;
  - IPv4-mapped IPv6 (`[::ffff:7f00:1]`);
  - 100.64/10, multicast and broadcast addresses;
  - single-label names (`http://router/`);
  - `.home.arpa`, `.internal` and `.lan`;
  - public names that resolve to a private address (`*.nip.io`, DNS
    rebinding). The app makes no DNS lookups (no network calls), so it
    cannot see them.
- **Mailto: only `to`, `cc` and `bcc` in the query are checked.**
  - A second address in the path (`mailto:a@x.com,b@evil.com`) is not
    warned on. It is shown, though: the headline is everything before the
    `?` (`src/lib/payload.ts:46`).
  - These are not tested:
    - Percent-encoded parameter names (`%62cc`).
    - `+` in an address. `URLSearchParams` would show it as a space, while a
      mail client keeps the `+`.
    - Other header fields (`reply-to`).
- **The card is not exercised by these criteria.**
  - Tone, `Open anyway` and ⌘O moving focus are existing code
    (`src/components/ResultCard.tsx:49-53`,
    `src/components/ResultCard.tsx:77`). Their tests cover an `http` link
    (`src/__tests__/AppKeys.test.tsx:45`,
    `src/__tests__/AppKeys.test.tsx:146-152`), not a mailto or a local host.
  - The claim that the new warnings make ⌘O move focus rests on reading
    those lines.
- **Wrapping is not checked.** `.warnings` sets no `overflow-wrap`
  (`src/styles.css:437-445`). A long recipient without spaces may run past
  the card's edge, as a long host in today's `userinfo` message may. The
  request says not to change how cards render warnings.
- **The voice is pinned only in part.** The tests pin the exact message for
  one mailto input and for LOCAL. Whether the wording reads right is a
  human's call.
