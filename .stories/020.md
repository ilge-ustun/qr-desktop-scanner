# Story 020: qr-core reads what networksetup, screencapture, CoreGraphics and open report; a failed open and a failed shortcut save stop reporting success

## Symptom

Read on epic/core at 5767054.

**Two failures are silent.**

- Open Settings reports success when `open` fails. `open_screen_settings`
  runs `/usr/bin/open` with `.status()` and then `.map(|_| ())`
  (`src-tauri/src/platform/macos.rs:37-43`). Each exit status gives `Ok(())`.
  Only a failure to start `open` gives an error.
- A new shortcut that cannot be saved is lost at the next launch. `change`
  registers the new shortcut, makes it current, and then drops the result of
  `save` with `let _ =` (`src-tauri/src/hotkey.rs:124-131`). The chip shows
  the new shortcut and it scans. At the next launch `register_saved` reads the
  old file, so the old shortcut or ⌘⇧2 comes back
  (`src-tauri/src/hotkey.rs:70-81`). Nothing tells the user.

**The rules that read macOS's output have no test.** They are in
`src-tauri/src/platform/macos.rs`, which compiles only for macOS
(`src-tauri/src/platform.rs:6-14`). No test on Linux reaches them:

- the networksetup arguments, without an empty password
  (`src-tauri/src/platform/macos.rs:119-123`);
- networksetup's result: a failed join prints on stdout and exits 0, and
  success prints nothing (`src-tauri/src/platform/macos.rs:128-142`);
- screencapture's result: a written file is Taken, exit 0 or 1 with no file
  is Cancelled, and the rest is an error
  (`src-tauri/src/platform/macos.rs:57-64`);
- the CoreGraphics display count (`src-tauri/src/platform/macos.rs:96-102`);
- the names of the per-display files
  (`src-tauri/src/platform/macos.rs:73-75`).

**Error conversion repeats.** `map_err(|e| e.to_string())` is at
`src-tauri/src/commands.rs:41`, `src-tauri/src/commands.rs:44`,
`src-tauri/src/commands.rs:53`, `src-tauri/src/commands.rs:56`,
`src-tauri/src/hotkey.rs:55`, `src-tauri/src/hotkey.rs:57` and
`src-tauri/src/hotkey.rs:58`.

## Acceptance criteria

The ACs name six public functions. Their names, paths and signatures are
fixed, so that a probe in core/tests can call them:

- in `core/src/wifi.rs`:
  `qr_core::wifi::join_args(device: &str, ssid: &str, password: Option<&str>) -> Vec<String>`
  and
  `qr_core::wifi::join_result(success: bool, status: &str, stdout: &str, stderr: &str) -> Result<(), String>`;
- in a new module core/src/capture.rs, declared `pub mod capture;` in
  `core/src/lib.rs`:
  `qr_core::capture::selection_verdict(file_written: bool, code: Option<i32>, status: &str) -> Result<Capture, String>`
  (`Capture` is `qr_core::Capture`),
  `qr_core::capture::display_count(err: i32, count: u32) -> Result<u32, String>`,
  `qr_core::capture::display_files(dir: &Path, count: u32) -> Vec<PathBuf>`
  and
  `qr_core::capture::open_settings_result(success: bool, status: &str, stderr: &str) -> Result<(), String>`.

`status` is the exit status as the shell writes it (`ExitStatus`'s `Display`,
for example `exit status: 4`). The functions use it only in a message. `code`
is `ExitStatus::code()`, which is `None` when a signal stopped the process.
The command output in the tables is made up for the tests. Nobody has seen
these commands print it.

Each instrument is a Rust test in qr-core: in the module's `tests` module, as
`core/src/wifi.rs:58-113` has, or in a new file in core/tests. It asserts the
exact return value for each row of its table, with `assert_eq!` on the whole
`Vec` or `Result`. On today's tree each test fails to compile, because the
function does not exist.

## Known weakness of the instrument

- **The real commands' output is not observed here.** The tests encode the
  quirks as the code documents them today: networksetup exits 0 on a failed
  join and prints the reason on stdout
  (`src-tauri/src/platform/macos.rs:128-129`); screencapture exits 0 or 1 on
  Esc, by macOS version (`src-tauri/src/platform/macos.rs:60`). Nobody has
  seen, for this story: what `open` prints and returns when it fails; that
  the first line of networksetup's output is the useful one; that
  networksetup takes an SSID that starts with `-` as the SSID and not as an
  option. AC1 proves only that the SSID is one argument, in third place.
- **No instrument sees macos.rs call core.** `scripts/check-macos-shell.sh`
  type-checks and lints macos.rs. It runs nothing. Clippy does not warn
  about an unused public function in qr-core. A builder who adds the six
  functions and leaves macos.rs as it is passes AC1 to AC6. Item 1 of "Also
  required" is checked by reading macos.rs's diff, and by a person on a Mac.
- **The stub is compiled nowhere** (Evidence 6). This story keeps it right
  by keeping the public items of macos.rs. If a later change alters them,
  nothing here sees the stub go wrong.
- **Items 3 and 4 of "Also required" have no test.** The shell has no test
  that runs on Linux. A person checks that the page gets the same strings as
  today, and that a failed save puts the previous shortcut back (Human
  verification). The person can cause three of the converted errors by hand:
  the URL guard, the Wi-Fi check, a shortcut with no modifier. Nobody causes
  the opener error, the error from awaiting `spawn_blocking`, or the JSON
  error.
- **The page shows nothing for a failed Open Settings** (Evidence 3).
- **The shortcut error can be cut off** (Evidence 4). Not measured.
- **The exit status as the shell reads it.** The functions trust what the
  shell gives them. That `status.code()` is `Some(1)` for exit 1, and that
  `success()` is the same as code `Some(0)`, is std's documented behaviour on
  Unix. It is not observed here.
- **The whole-screen status check stays in the shell** (Evidence 2), with no
  test.
