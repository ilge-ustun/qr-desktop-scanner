# Story 009: CI tokens get least privilege, the release checkout keeps no credential and restores no Rust cache, and Dependabot also updates npm and cargo

## Symptom

Three findings from the security review. I confirmed each in the current
files.

1. **`.github/workflows/macos.yml` has no `permissions` key.** Its token
   gets whatever the repository's default is. That may be write. The file
   runs on pushes to `main` and `develop`, on pull requests and by hand
   (`.github/workflows/macos.yml:7-11`).
2. **The release job runs third-party code with a write token in
   `.git/config`.** The workflow grants `contents: write`, `id-token: write`
   and `attestations: write` (`.github/workflows/release.yml:12-15`). The
   checkout (`.github/workflows/release.yml:21`) sets no `with`, so
   `persist-credentials` is left at its default, `true`. The job then runs
   `npm ci`, `cargo test --workspace` and `tauri build`
   (`.github/workflows/release.yml:42-46`). Each runs code from
   dependencies: npm install scripts and every crate's build script. Any of
   them can read the token from the git config. The job also restores
   `Swatinem/rust-cache` (`.github/workflows/release.yml:40`). That cache
   holds `~/.cargo` and `target/`, written by earlier runs, and the release
   is built on top of it.
3. **Dependabot updates only the pinned actions.** `.github/dependabot.yml:4-8`
   has one entry, `github-actions`. Nothing proposes npm or cargo updates.

## Evidence

I read the files at `epic/quality` (0adbdd2, the same commit as `develop`).
Nothing was built, run or measured. I did not read the repository's
settings on GitHub.

### macos.yml

- No line of `.github/workflows/macos.yml:1-39` is a `permissions` key, at
  the top level or under the job.
- Its token is used by the checkout (`.github/workflows/macos.yml:17`). The
  npm cache (`.github/workflows/macos.yml:21`), `Swatinem/rust-cache`
  (`.github/workflows/macos.yml:26`) and `actions/upload-artifact`
  (`.github/workflows/macos.yml:36`) talk to the runner's cache and artifact
  services. GitHub's docs say those use the runner's own token, not the
  `GITHUB_TOKEN` scopes (not observed). No step pushes, comments, labels or
  publishes. So `contents: read` should be enough. The next macOS CI run
  shows it.
- Pull requests from forks get a read-only token anyway. Pushes to `main`
  and `develop`, and manual runs, get the repository default. I could not
  read that default. A top-level block makes the setting irrelevant.

### release.yml

- The request says the permissions are granted "to the whole job". They are
  granted to the whole workflow, at the top level
  (`.github/workflows/release.yml:12-15`). There is one job, `release`
  (`.github/workflows/release.yml:18`), so the effect is the same.
- actions/checkout v4's docs say that `persist-credentials: true` writes
  the token into the local git config, as an `extraheader` for
  `https://github.com/` (not observed; the action's source is not in this
  repo).
- **Who could read it.** `npm ci` runs on macOS, so `fsevents` and its
  install script are installed (`package-lock.json:2451`). The cargo steps
  run the build script of every crate in `Cargo.lock`, and of the shell
  (`src-tauri/build.rs:1-3`).
- **No step needs the git credential.** I checked each step of
  `.github/workflows/release.yml:21-66`:
  - The tag check (`:23-29`) reads `tauri.conf.json` with `node` and reads
    `$GITHUB_REF_NAME`.
  - setup-node, rust-toolchain and rust-cache are at `:31-40`.
  - `npm ci`, `npm test`, `cargo test` and `tauri build` are at `:42-46`.
  - The DMG step (`:50-54`) runs `cp` and `shasum`.
  - `actions/attest-build-provenance` (`:56-58`) uses OIDC and its own
    `github-token` input.
  - The publish step (`:60-66`) runs `gh release create` with `GH_TOKEN`
    from `env` (`:62`). The tag already exists, because pushing it started
    the run. So gh creates the release through the API and pushes nothing.
    gh finds the repository from the `origin` remote's URL, and
    `persist-credentials: false` leaves that URL in place.
  - No step runs `git push`, `git fetch` or `git tag`.
  - No dependency is fetched with git: `Cargo.lock` has no
    `source = "git…"` and `package-lock.json` has no `"resolved": "git…"`.
  - So publishing should be unaffected. That is read from the files, and
    not observed until the next tag.
- **rust-cache.** I checked the whole file: `.github/workflows/release.yml:40`
  is its only cache step besides setup-node's `cache: npm` (`:34`).
  **Coordinator's choice (delegated by the human):** remove the rust-cache
  step from the release job, so each release builds from a clean cache. A
  release then takes a few minutes longer (not measured). `macos.yml` keeps
  its rust-cache.
- **Not in this story:** splitting the job into a build job and a publish
  job. That changes the release path just before v0.2.0. A later story may
  do it.

### dependabot.yml

- `.github/dependabot.yml:5-8` is the only entry: `github-actions`,
  directory `/`, weekly. It has no `target-branch`, so its PRs go to the
  repository's default branch. The coordinator's intent keeps it as it is.
- `Cargo.toml:1-3` is the workspace root, with members `core` and
  `src-tauri`, and there is one `Cargo.lock` at the root. `package.json` and
  `package-lock.json` are at the root too. So `/` is the directory for both
  new ecosystems.
- `develop` is the integration branch. `main` takes only releases. So both
  new entries use `target-branch: develop`.
- **Grouping.** In each new ecosystem, minor and patch updates are grouped
  into one PR. A major update still comes as its own PR, one per dependency.
  The group names `patterns: ["*"]` explicitly, so that it covers every
  dependency whether or not Dependabot needs `patterns`.
- **A consequence of grouping per ecosystem.** The `tauri` crate (2.12.5,
  `Cargo.lock:4340-4341`) and `@tauri-apps/api` (2.12.4,
  `package-lock.json:1109-1110`) are updated in different PRs. The Tauri
  CLI may refuse to build when its npm and Rust packages differ in
  major.minor. I did not check that against the CLI. If it does, a Tauri
  minor update needs the npm PR and the cargo PR merged together.
- GitHub's docs say Dependabot reads `dependabot.yml` from the default
  branch only (not observed). So the new entries take effect when this
  change reaches the default branch, not when it merges to `develop`.
- The comment at `.github/dependabot.yml:1-2` speaks only of actions. The
  builder may reword it to cover all three ecosystems. Nothing tests it.

### Writing the test

- vitest collects only `src/**/*.test.{ts,tsx}` (`vite.config.ts:12`). So
  the new test has to live under `src/`. **This differs from the request,
  which lists `src/**` as out of scope.** As in story 008, `scope_deny`
  names the product code and every existing test, and leaves room for one
  new test file. It must be a `.ts` file under `src/__tests__/`:
  `src/__tests__/*.tsx` is denied.
- The existing file-reading tests use Vite's `?raw` import
  (`src/__tests__/docsDescribeApp.test.ts:9-10`,
  `src/__tests__/siteReadyPopover.test.ts:7`). `tsconfig.json:14` sets
  `"types": ["vite/client"]`, which types `?raw`. `@types/node` is not
  installed, so a `node:fs` import would fail `tsc --noEmit`.
- Importing from `.github/` with `?raw` has not been tried (not observed).
- No YAML parser is installed. `yaml` appears in `package-lock.json` only
  as an optional peer dependency of vite (`package-lock.json:3690`). There
  is no `node_modules/yaml` entry. `package.json` and `package-lock.json`
  are denied.

## Acceptance criteria

The instrument for all four criteria is one new vitest `.ts` file under
`src/__tests__/`. It reads the three YAML files as text, with a small
line reader:

- A `#` at the start of a line, or after a space or tab, begins a comment,
  and the reader drops it with the rest of the line. It then drops trailing
  whitespace, and drops each line left empty.
- A line's indent is its count of leading spaces.
- A **key line** is `<key>:` with an optional value after `: `. A
  **key's block** is the lines after it with a greater indent, up to the
  first line without one.
- A **list item** starts at a line whose text begins `- `. What follows the
  `- ` is read as a key line. The item is that line plus the following lines
  indented more than its `-`. A **step** is a list item in a `steps` key's
  block.
- Before a value is compared, one pair of surrounding `"` or `'` is removed,
  except where a criterion says otherwise.

The reader handles block style only: one key, or one list item, per line.
The builder writes the three files that way, as they are now. Flow style
(`{…}` or `[…]`) counts as a failure.

**AC1 — `.github/workflows/macos.yml` grants its token `contents: read` at the top level, and nothing else.**
Instrument: the new test reads `.github/workflows/macos.yml`.
(a) Exactly one line of the file is a `permissions` key. Its indent is 0
and it has no value on the line.
(b) Its block is exactly one key line: `contents: read`.
(c) No line of the file contains the word `write`. That excludes both
`write` and `write-all`.
Fails on the base: the file has no `permissions` key.
Goes red when:
- the block is deleted;
- `contents: read` becomes `contents: write`;
- `pull-requests: write` is added to the block;
- the block is replaced by `permissions: read-all` on one line;
- the block is indented under `build:` instead of being at the top level;
- the top-level block stays and `permissions: write-all` is added under
  `build:`.

**AC2 — In `.github/workflows/release.yml`, each step whose `uses` starts with `actions/checkout@` sets `persist-credentials: false`, and no line names `rust-cache` or `actions/cache`.**
Instrument: the same test reads `.github/workflows/release.yml`.
(a) At least one step has a `uses` key whose value starts with
`actions/checkout@`. Each such step has a `with` key line among its lines,
and that key's block contains the key line `persist-credentials: false`.
The value must be exactly `false`, unquoted.
(b) No line of the file contains `rust-cache` or `actions/cache`.
`cache: npm` in the setup-node step (`.github/workflows/release.yml:34`)
matches neither.
Fails on the base: the checkout at `.github/workflows/release.yml:21` has
no `with`, and `.github/workflows/release.yml:40` uses
`Swatinem/rust-cache`.
Goes red when:
- `persist-credentials: false` is removed;
- it becomes `persist-credentials: true`;
- it moves into the `with` block of the `actions/setup-node` step;
- it is commented out;
- a second `actions/checkout@<the same sha>` step without it is added after
  the tag check;
- the `Swatinem/rust-cache@d1527c8f67ef9af357290475d4af4b0fab8f12e0` step
  is put back;
- that step is replaced by an
  `actions/cache@<sha>` step with `path: target`.

**AC3 — Paired with AC1 and AC2: release.yml keeps its three permissions and its one job, and each `uses` value in macos.yml and release.yml stays pinned to a 40-hex commit SHA.**
Instrument: the same test.
(a) In `.github/workflows/release.yml`, exactly one line is a `permissions`
key. Its indent is 0 and it has no value on the line. Its block's key
lines are exactly `contents: write`, `id-token: write` and
`attestations: write`, in any order.
(b) The block of release.yml's `jobs` key has exactly one key line at the
indent next below `jobs`, and that line is `release:`.
(c) In `.github/workflows/macos.yml` and `.github/workflows/release.yml`,
every `uses` value matches
`^[A-Za-z0-9_.-]+/[A-Za-z0-9_./-]+@[0-9a-f]{40}$`. That covers a `uses`
key line and a `uses` after `- `. The test checks the form, not the SHA
itself, so a Dependabot SHA bump still passes.
Passes on the base. This is a guard, and its value is in its reds.
Goes red when:
- release.yml's `contents: write` becomes `contents: read`
  (`gh release create` at `.github/workflows/release.yml:64` needs write);
- `id-token: write` is dropped (the attestation at
  `.github/workflows/release.yml:56` needs it);
- `actions: write` is added to release.yml's block;
- release.yml's job is split into `build` and `publish` jobs;
- `actions/checkout@11d5960a326750d5838078e36cf38b85af677262` becomes
  `actions/checkout@v4` in either file;
- macos.yml's
  `Swatinem/rust-cache@d1527c8f67ef9af357290475d4af4b0fab8f12e0` becomes
  `Swatinem/rust-cache@v2`.

**AC4 — `.github/dependabot.yml` adds weekly npm and cargo entries for `/` that target `develop` and group minor and patch updates, and keeps the github-actions entry as it is.**
Instrument: the same test reads `.github/dependabot.yml`.
(a) The file has the line `version: 2` at indent 0.
(b) The `updates` key, at indent 0, has exactly three list items. Their
`package-ecosystem` values are `github-actions`, `npm` and `cargo`, each
once.
(c) The github-actions item's lines, after the reader has run (comments,
blank lines and trailing whitespace dropped, indentation kept), are exactly
the four lines at `.github/dependabot.yml:5-8`:

```
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
```

(d) The npm item and the cargo item each have exactly these key lines at
the item's key indent, and no others:
- `package-ecosystem`;
- `directory`, value `/`;
- `schedule`, whose block is exactly `interval: weekly`;
- `target-branch`, value `develop`;
- `groups`.
(e) Each of those `groups` blocks has exactly one group: one key line at

- `patterns`: its list is exactly one item, `"*"` or `'*'`. Here the quotes

- `update-types`: its list is exactly `minor` and `patch`, in either order.
Fails on the base: `updates` has one item.
Goes red when:

- cargo's `interval` becomes `daily`;
- npm's `directory` becomes `/site`;

- `patch` is removed from cargo's `update-types`;
- cargo's `groups` is removed;
- npm's `patterns` item becomes `"@tauri-apps/*"`;
- npm's `patterns` item becomes a bare `*`;

## Known weakness of the instrument

- **These workflows run only on GitHub.** The test reads text. It does not
  run a workflow or ask Dependabot anything.
  - **macos.yml:** the next macOS CI run after this lands on `develop`
    shows that `contents: read` is enough for its checkout, both caches
    and the artifact upload.
  - **release.yml:** first exercised by the next tag, v0.2.0. Until then,
    nothing has run the release with `persist-credentials: false` and
    without rust-cache. That publishing still works rests on the step-by-step
    reading in Evidence.
  - **dependabot.yml:** GitHub validates it, and only after it reaches the
    default branch (GitHub docs, not observed). That `groups` with
    `update-types` gives one PR per ecosystem for minor and patch updates is
    GitHub's documented behaviour. It is not observed here.
- **A YAML subset, not a YAML parser.** The test proves named keys and
  values sit at named places in the text. It does not prove that the files
  are valid YAML, or valid workflow or Dependabot syntax. Tabs, anchors,
  aliases, merge keys, quoted keys and multi-line flow style are not
  modelled. GitHub may read such a file differently from the test. A file
  GitHub cannot parse shows as a failed or invalid run on GitHub, not in
  vitest.
- **AC2 checks the git config path only.** `persist-credentials: false`
  keeps the token out of `.git/config`. The job still grants
  `contents: write`, `id-token: write` and `attestations: write`. Every step
  still runs in that one job, `npm ci` and the cargo build scripts
  included. GitHub's docs say that with `id-token: write`,
  `ACTIONS_ID_TOKEN_REQUEST_URL` and `ACTIONS_ID_TOKEN_REQUEST_TOKEN` are in
  the environment of every step (not observed). So a hostile build script
  could still ask for the workflow's OIDC token. Closing that needs the
  build/publish split, which is out of scope.
- **The checkout's behaviour is the action's.** That the default writes
  the token into the git config, and that `false` keeps it out, is from
  actions/checkout's docs. It is not observed. The test only proves the
  input is set.
- **Security updates may ignore `target-branch`.** If Dependabot security
  updates are enabled on the repository, GitHub's docs say they open PRs
  against the default branch whatever `target-branch` says (not
  observed).
- **Tauri updates may need two PRs merged together.** See Evidence. No
  criterion covers it.

## Out of scope

- **`.github/workflows/pages.yml`:** the request excludes it. It already
  declares its permissions.
- **Splitting the release job** into build and publish jobs. Not just
  before a release; a later story may do it. AC3 (b) holds the job count at
  one.
- **Anything else in the three files.** No other step, trigger or action
  changes. A one-line comment beside a change is fine. These stay as they
  are:
  - macos.yml's checkout, which keeps `persist-credentials` at its default.
    With `contents: read`, that token can only read a public repository.
  - macos.yml's rust-cache.
  - release.yml's `cache: npm`. `npm ci` checks each tarball against its
    integrity hash in `package-lock.json`.
- **`.github/release-notes.md`:** release text, not this story.
- **`src/` product code** (`src/App.tsx`, `src/main.tsx`, `src/styles.css`,
  `src/components/*`, `src/lib/*`) and **the existing tests**. The new
  criteria go in one new `.ts` file under `src/__tests__/`.
- **`core/*`, `src-tauri/*`, `Cargo.toml`, `Cargo.lock`:** no Rust changes.
- **`package.json`, `package-lock.json`, `tsconfig.json`,
  `vite.config.ts`, `eslint.config.js`:** no new dependency or setting.
  In particular, no YAML parser.
- **`site/*`, `scripts/*`, `index.html`, `README.md`:** nothing to say
  there.
- **`CLAUDE.md`, `AGENTS.md`:** the human's files.
