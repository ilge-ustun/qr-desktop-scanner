# Story 015: A push that changes only the fleet's state (.stories/, .review/, .blocked/) does not start a macOS build

## Symptom

`.github/workflows/macos.yml` builds on every push to `main` and `develop`
(`.github/workflows/macos.yml:7-9`). It has no path filter. The fleet
pushes its own state to `develop` several times per story: draft, promoted
to ready, in_progress, done, merged into epic/…. These commits change only
`.stories/` and `.review/`. Each push starts a full macOS build: `npm ci`,
lint, tests, clippy, `cargo test` and a Tauri bundle
(`.github/workflows/macos.yml:32-39`). No code changed, so the build is
wasted.

The coordinator reports these numbers. I did not measure them again. In a
few hours, about 60 such builds ran. 56 passed. 2 failed: GitHub cancelled
the job with "The job was not acquired by Runner of type hosted even after
multiple attempts" and "Due to capacity constraints, jobs targeting macOS
arm64 runners may experience longer queue times" (runs 39754529724 and
39754486817). For those two, the human got "macOS build: All jobs were
cancelled" emails.

The top comment of the file says "Every change gets a real macOS build"
(`.github/workflows/macos.yml:3-4`).

## Evidence

I read the files at `epic/quality` (5b8e114) and the history of `develop`
(bdd5767). Nothing was built, run or measured. I did not read the Actions
runs on GitHub.

### The premise holds

- `.github/workflows/macos.yml:7-11` is the whole trigger block. `push` has
  `branches: [main, develop]`. `pull_request:` and `workflow_dispatch:`
  have nothing under them. No line of the file is a `paths` or
  `paths-ignore` key.
- `develop` has 65 commits whose subject starts `story(`. Together they
  make 697 file changes under `.review/` and 65 under `.stories/`. They
  change no file outside these two directories
  (`git log develop --grep='^story(' --name-only`).
- The last epic landing on `develop` is 0adbdd2 (22 Oct, 02:26). All 30
  commits on `develop` after it are `story(` commits.
- 65 commits agree with "about 60 builds" if some commits were pushed
  together. I did not check that.
- The repo already has a path filter: `.github/workflows/pages.yml:8-10`
  uses `paths` on `push`.

### Differences from the request

- **No commit on `develop` has changed `.blocked/`.**
  `git log develop -- .blocked` is empty. The template says a builder writes
  `.blocked/<id>.md` when it halts. The pattern stays in the list, as the
  request asks. If the fleet commits a halt note to `develop` later, that
  push does not build.
- **`.fleet/` is not in the list.** d4e9081 changed only `.fleet/config`
  and `.fleet/rules.md`. A push like that still builds. This follows the
  request. Such pushes are rare (two commits so far). A later story can add
  the pattern.
- **The filter has an effect only where the pushed commit has it.** GitHub
  uses the workflow file of the pushed commit (GitHub docs, not observed).
  This story merges into `epic/quality`. Fleet-state pushes to `develop`
  continue to build until `epic/quality` lands on `develop`. On `main`,
  the filter starts when a release merges it there.

### What changes, in `.github/workflows/macos.yml` only

1. Under `on.push`, add `paths-ignore` with three patterns: `.stories/**`,
   `.review/**` and `.blocked/**`. Use block style: one `- ` item per line,
   indented more than `paths-ignore:`. Keep `branches: [main, develop]` as
   it is, on its one line.
2. **Coordinator's choice (delegated by the human):** `pull_request` and
   `workflow_dispatch` stay as they are, with nothing under them. A pull
   request into `main` (the release path) and a manual run always build.
   There is a second reason. GitHub's docs say that when a path filter skips
   a workflow, its required checks stay pending (not observed). With no
   filter on `pull_request`, a required macOS check on a PR into `main`
   cannot hang.
3. Write a new top comment in place of `.github/workflows/macos.yml:3-4`.
   It states the exception: a push that changes only the fleet's state
   (`.stories/`, `.review/`, `.blocked/`) does not build. It states why: no
   code changed, so the build was wasted, and these builds filled the macOS
   queue at a time when GitHub dropped jobs for lack of runners. It also
   states that pull requests and manual runs always build. Keep the lines about SHA pins and Dependabot (`:5-6`) and the
   permissions comment (`:13`).
4. Nothing else in the file changes. That includes the `permissions` block
   (`:14-15`, story 009), the job, every step and every SHA pin
   (`:17-43`). The diff of this file against `epic/quality` touches only
   lines 3-11.

### How GitHub reads the filter

All of this is from GitHub's docs ("Workflow syntax", `on.push.paths-ignore`).
None of it is observed.

- If every file that a push changes matches a `paths-ignore` pattern, the
  workflow does not run. If one file does not match, it runs.
- A push must satisfy `branches` and `paths-ignore` together.
- `*` does not match `/`. `**` matches any characters, `/` included. So
  `.review/**` matches `.review/001/round-1/baseline/build.log`.
  `.review/*` does not.
- One event cannot have both `paths` and `paths-ignore`. `paths` names the
  files that start a run. With these three patterns, `paths` would build
  only the fleet-state pushes: the opposite of the intent.
- For a push, GitHub compares the commit before the push with the commit
  after it. A merge of an epic into `develop` changes code, so it builds.

## Acceptance criteria

The instrument for both criteria is vitest. It reads
`.github/workflows/macos.yml` as text with the reader at
`src/__tests__/ciConfig.test.ts:14-67`:

- A `#` at the start of a line, or after a space or tab, starts a comment.
  The reader drops it with the rest of the line. Then it drops trailing
  whitespace and each line that is left empty.
- A line's indent is its count of leading spaces.
- A **key line** is `<key>:` with an optional value after `: `. A key's
  **block** is the lines after it with a greater indent, up to the first
  line without one. A block's **own indent** is the smallest indent in it.
- **Unquoted** means that one pair of matching surrounding `'` or `"` is
  removed.

**AC1 — In `.github/workflows/macos.yml`, `on.push` has a `paths-ignore` list of exactly `.stories/**`, `.review/**` and `.blocked/**`, and no other key except `branches`.**
Instrument: the vitest test above.
(a) Exactly one line of the file is an `on` key. Its indent is 0 and it
has no value.
(b) Exactly one line of the file is a `push` key. It is in the `on` block,
at that block's own indent, and it has no value.
(c) The lines at the `push` block's own indent are exactly two key lines:
`branches` and `paths-ignore`. So the block has no `paths`,
`branches-ignore` or `tags` key.
(d) The `paths-ignore` key line has no value. Its block is exactly three
lines. Each line starts with `- `, and the three lines have the same
indent.
(e) The three item values, unquoted, are `.stories/**`, `.review/**` and
`.blocked/**`, each one time, in any order. The test accepts each value
bare, in `'…'` or in `"…"`.
Fails on the base: the `push` block has only `branches: [main, develop]`.
Goes red when, in `.github/workflows/macos.yml`:
- the `.blocked/**` item is removed;
- an item `'**'` is added to the list;
- an item `'src/**'` is added to the list;
- `.review/**` becomes `.review/*`;
- `paths-ignore:` becomes `paths:`;
- a `paths:` key with the item `'src/**'` is added next to `paths-ignore`;
- the list is written in flow style:
  `paths-ignore: ['.stories/**', '.review/**', '.blocked/**']`;
- the four `paths-ignore` lines are commented out;
- the `paths-ignore` key and its list move from `push` to `pull_request`;
- the `paths-ignore` key and its list move up one level, next to `push` in
  the `on` block.

**AC2 — Paired with AC1: `push` still covers `main` and `develop`, and `pull_request` and `workflow_dispatch` stay with no filter.**
Instrument: the same test.
(a) In the `push` block, the `branches` key line's text is exactly
`branches: [main, develop]`.
(b) The lines at the `on` block's own indent are exactly three key lines:
`push:`, `pull_request:` and `workflow_dispatch:`, in any order. None has a
value.
(c) The blocks of `pull_request` and `workflow_dispatch` are empty: no line
after either has a greater indent before the next line at the `on` block's
own indent. So neither has `paths`, `paths-ignore`, `branches` or `types`.
Passes on the base. This is a guard. Its value is in its reds.
Goes red when, in `.github/workflows/macos.yml`:
- `branches: [main, develop]` becomes `branches: [main]`;
- it becomes `branches: [main, develop, 'epic/**']`;
- a copy of the `paths-ignore` key and its three items is added under
  `pull_request` (AC1 still passes);
- a `paths:` key with the item `'src/**'` is added under `pull_request`;
- `branches: [main]` is added under `pull_request`;
- `pull_request:` is removed;
- `workflow_dispatch:` is removed.

## Known weakness of the instrument

- **GitHub reads the filter, not the test.** The test proves that named
  keys and values are at named places in the text. That GitHub then skips a
  push whose files all match, and builds any other push, is from GitHub's
  docs. It is not observed. The first observation comes after
  `epic/quality` lands on `develop`:
  - The landing merge changes code, so it builds one time. That is
    expected.
  - The first fleet-state push after it shows no new run in
    `gh run list --workflow macos.yml --branch develop`.
- **Until `epic/quality` lands on `develop`, nothing changes there.**
  GitHub uses the workflow file of the pushed commit. Fleet-state pushes to
  `develop` continue to build until then.
- **A push of more than 300 files.** GitHub's docs say diffs are limited
  to 300 files. If a changed file that does not match is not in the first
  300 that GitHub reads, the workflow does not run (not observed). A `done`
  commit changes about 30 files (cd369b2 changes 30). An epic landing
  changes code only, because its `.review/` files are already on `develop`.
  So I expect no push near the limit. Nothing checks this.
- **This does not show that the cancelled jobs stop.** The cancels come
  from GitHub's macOS runner capacity. This story removes the fleet-state
  builds from the queue. A push that changes code can still be cancelled
  the same way.
- **A YAML subset, not a YAML parser.** The test does not prove that the
  file is valid YAML or valid workflow syntax. It does not model tabs,
  anchors, quoted keys, or a `- ` item at its key's own indent (YAML
  allows that; the reader does not, so AC1 (d) requires deeper items).
  GitHub can read such a file differently from the test. If GitHub cannot
  parse the file, that shows on GitHub as a failed run, not in vitest.
- **Two requirements have no criterion.**
  - The top comment. The reader drops comments, so no test reads it. The
    human and the reviewer read it.
  - The rest of the file. Story 009's tests still hold the permissions
    (`src/__tests__/ciConfig.test.ts:107-117`) and the SHA-pin form
    (`src/__tests__/ciConfig.test.ts:165-173`). No test holds the job and
    its steps. The reviewer reads the diff: it touches only
    `.github/workflows/macos.yml:3-11`. An `if:` added to the job, for
    example, is caught only by that reading.
- **`.fleet/` pushes still build.** See Evidence. This follows the
  request.
