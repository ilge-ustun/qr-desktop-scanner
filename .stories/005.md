# Story 005: Result cards answer the keyboard: Enter copies, ⌘O opens a safe link, ⌘J connects

## Symptom

I read the files at `a531315`, the tip of `epic/cards`, and ran nothing.

The result cards have no keyboard shortcuts. The page has only two keydown
listeners:

- `src/App.tsx:52-55`: Esc hides the popover. Nothing else.
- `src/components/HotkeyButton.tsx:28-42`: a listener on `window`, in the
  capture phase, present only while the chip records a new global shortcut.
  It calls `preventDefault()` and `stopPropagation()` on every key.

No component under `src/components/` handles a key. So a person who has just
scanned a code must use the mouse to copy, open or connect. The actions the
keys should run all exist today as buttons:

- **Link, email and text cards** (`GenericCard`, `src/components/ResultCard.tsx:43`):
  - `Copy` calls `onCopy(payload.text)` (`src/components/ResultCard.tsx:95`).
  - `Open` is shown when the link is openable and has no warnings
    (`src/components/ResultCard.tsx:100`).
  - `Open anyway` is shown when the link is openable and has warnings
    (`src/components/ResultCard.tsx:102-104`).
- **Contact, phone, SMS and geo cards** (`FieldCard`):
  - The headline's Copy (`Copy name`, `Copy number`, `Copy place`,
    `Copy coordinates`) copies the headline (`src/components/FieldCard.tsx:84-91`).
  - The card's one other action is drawn at `src/components/FieldCard.tsx:92`.
    It is `Open in Maps` on a geo card with valid coordinates
    (`src/components/GeoCard.tsx:25`).
- **Wi-Fi card**:
  - `Copy password` is shown only when there is a password
    (`src/components/WifiCard.tsx:67-75`).
  - `Connect` (`src/components/WifiCard.tsx:76-78`) is disabled while
    `Connecting…` and once `Connected`.

## Known weakness of the instrument

- **Keyboard activation is modelled, not observed.**
  - jsdom does not turn an Enter keydown into a click on a focused button.
    That is why `@testing-library/user-event` simulates it. I did not run it
    here.
  - AC3 fires the click itself and checks that the keydown was not
    cancelled. That a browser then presses the button is the HTML
    activation behaviour, not observed. Whether WebKit presses on keydown or
    on keyup does not change these tests.
- **Focus on a Mac is not seen.**
  - WebKit on macOS does not focus a button that is clicked with the mouse.
    So for a mouse user, focus usually stays nowhere and the keys act on the
    first card.
  - Whether Tab reaches the card buttons in the popover's WKWebView may
    depend on macOS's Keyboard navigation setting.
  - Neither was observed. Human verification covers both.
- **That the page receives ⌘O and ⌘J is not observed.**
  - The app sets no menu with those keys. `src-tauri/src/tray.rs:4` builds
    only the tray menu.
  - Whether WKWebView, or the system, takes ⌘O or ⌘J before the page's
    keydown was not observed.
  - If the user has chosen ⌘O or ⌘J as the global scan shortcut, the OS-wide
    hotkey takes it first. That case is untested.
- **The popover must have keyboard focus.** Esc relies on this already. It
  was not observed for these keys.
- **The recording rule is checked only in the idle view.** Cards and the
  chip are never shown together (Evidence, discrepancy 1). AC4(c) shows that
  the chip still records ⌘O. It cannot show a card being left alone during
  recording, because the app never draws that state.
- **The hints have no instrument.** jsdom loads no CSS and does no layout.
  What the criteria do not prove:
  - that a hint is visible;
  - that it sits next to the right button;
  - that it uses two inks and square corners;
  - that its glyphs are in the mono face.

  The existing tests only show that the hints left the buttons' names, text
  and number unchanged. A person looks.
- **The callbacks are mocks.** The clipboard, `core::url_guard`, the Wi-Fi
  join and Maps never run.
- **Untested key variants.** These are unspecified, and odd behaviour on
  them is a gap in the spec, not a failure of these criteria:
  - ⌘ with Shift or Option (`⌘⇧O`, `⌥⌘J`), or ⌘ together with Ctrl;
  - `⌘Enter`, or Enter with Shift;
  - an upper-case `key: "O"`;
  - non-US layouts, where `key` and `code` disagree (Dvorak).
- **Untested window before a scan starts.** Between a click on `Scan again`
  and `scan://started`, the old cards are still shown, and keys still act on
  them. "While a scan runs" is checked from `started` on.
- **Untested Enter target inside a card.** No result card has a focusable
  element that is not a button, so Enter's "card that contains focus" case
  is never exercised.
- **Only some outcomes are checked.**
  - ⌘O's route through the card's own `open` is proven by the values only:
    the Maps link, and nothing opened on a warned card. A failed open's
    message after ⌘O is not checked.
  - Only ⌘J's success message is checked, not the failure message.
