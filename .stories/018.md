# Story 018: a stale scan directory is swept before the next scan and at launch, and the one-scan-at-a-time flag clears in a Drop

## Symptom

Two defects in the scan flow. Both were read on epic/core at 5767054, which
is the same tree as develop.

**1. A screenshot can outlive its scan.** run_scan and run_find_all keep the
scan's files in a `tempfile::TempDir` named `scan-XXXXXX` under `scratch`
(`core/src/scan.rs:132-137`). A drag scan writes selection.png into it; Find
all writes display-1.png, display-2.png and so on. The doc comment says the
directory "is removed when this returns, whatever the outcome"
(`core/src/scan.rs:58-59`). That is true for each return and for a panic:
TempDir's Drop runs on unwind, and the release profile does not set
`panic = "abort"` (`Cargo.toml:9-13`). It is false when the process ends while
the scan's blocking thread still holds the TempDir:

- Quit calls `app.exit(0)` (`src-tauri/src/tray.rs:44`). In tauri 2.12.5 (the
  version in `Cargo.lock`), the end of `App::run` is `std::process::exit`, which
  drops nothing that another thread holds.
- A crash or a force-quit (SIGKILL) has the same result.

No code in the repo looks for an old `scan-*` directory later. So the
directory, and the screenshot if one was written, stays in
~/Library/Caches/io.github.ilge-ustun.qr-desktop-scanner/ until macOS or the
user clears it. (The identifier is `src-tauri/tauri.conf.json:5`; the shell
passes `app_cache_dir()` as `scratch`, `src-tauri/src/scan.rs:60-66`.) This
breaks the CLAUDE.md rule "The screenshot is deleted when the scan ends,
whatever the outcome."

**2. The one-scan-at-a-time flag is cleared by hand.** `scan()` swaps
`ScanState.running` to true and returns at once if it was already true
(`src-tauri/src/scan.rs:33-39`). Then it awaits the scan and stores false
(`src-tauri/src/scan.rs:40-43`). If the task panics between the swap and the
store, the flag stays true. From then on, each hotkey press, tray Scan and
Find all returns at `src-tauri/src/scan.rs:38` with no message, until the
user relaunches the app.

## Evidence

All of this was found by reading the code. Nothing was built, run or observed
on a Mac.

**Item 1 is confirmed as reported.** What an orphaned directory holds depends
on when the process ended. `temp_dir` runs before the capture
(`core/src/scan.rs:69`, then `core/src/scan.rs:75`). So an exit while the
crosshair is up leaves an empty `scan-*` directory. An exit during the decode
leaves the screenshot in it. Unverified: screencapture is a child process,
and the app's exit may not end it. If so, screencapture can write
selection.png into the orphaned directory after the app has gone.

**Item 2 is real in its shape, but no panic reaches it today.** This is
different from the report:

- run_scan, run_find_all and the decoder run in
  `tauri::async_runtime::spawn_blocking` (`src-tauri/src/scan.rs:71-89`).
  Tokio catches a panic on that thread (tokio 1.54.0,
  runtime/task/harness.rs, `poll_future`). The `.await` then gets an `Err`,
  and `src-tauri/src/scan.rs:89` turns it into `ScanOutcome::Error`. After
  that, the store at `src-tauri/src/scan.rs:41-43` runs. **So a panic in
  the scan itself does not leave the flag set today.**
- The other code between the swap and the store is
  `src-tauri/src/scan.rs:56-70`. It calls `Permission.granted()` (an FFI
  call), `app_cache_dir()` and `create_dir_all` (both return a Result),
  `emit` (its Result is ignored) and `popover::hide`. The only panic sites
  there are `app.state::<Popover>()`, which panics only if Popover is not
  managed (it is, `src-tauri/src/lib.rs:30`), and `.lock().unwrap()` at
  `src-tauri/src/popover.rs:55`, which panics only if an earlier panic
  poisoned that mutex while it was held.
- So item 2 is latent, and its fix is hardening. When the flag clears in a
  Drop, a later edit to this function cannot skip the clear. The later story
  that merges run_scan and run_find_all is one such edit. Item 1 also needs
  the rule written down: the sweep before a scan is safe only when one scan
  runs at a time.

**Coordinator's choice (delegated by the human, 22 Oct 2026): keep item 2.**
Story 019 rewrites this function next, and a flag that clears in a Drop
survives that rewrite. AC4 stays.

**The fakes are not in `core/tests/common/mod.rs`.** The report says they
are. That file holds only image helpers (`qr`, `canvas`, `paste`). The fake
ScreenPermission and Capturer are local to `core/tests/scan.rs:50-87`, and the
fake DisplaysCapturer to `core/tests/find_all.rs:14-107`. The tests below go
into those two files, beside their fakes.

**The cache directory is not only for scans.** Unverified: WebKit can keep
its own caches under ~/Library/Caches/<bundle id>/. For this reason the sweep
removes only `scan-*` directories and keeps everything else.

## Acceptance criteria

What to add, in qr-core, re-exported from `core/src/lib.rs:11-14`:

- `pub fn sweep_stale(scratch: &Path)`. It removes each directory directly
  under `scratch` whose name starts with the prefix that `temp_dir` uses
  (`"scan-"`, `core/src/scan.rs:134`; use one constant for both). It returns
  nothing. If it cannot read `scratch`, it returns. If it cannot remove an
  entry, it goes on to the next one. A scan never fails because of the
  sweep. It does not touch anything else under `scratch`, or anything
  outside `scratch`.
- run_scan and run_find_all call it before `temp_dir` makes their own
  directory. A call with no permission may sweep or not.
- `SingleFlight`: `Default`, `Send + Sync`, plain std (an atomic), with
  `try_start(&self) -> Option<guard>`. While no guard lives, it returns
  `Some(guard)`. While a guard lives, it returns `None`. Dropping the guard
  clears the flag.
- In the shell, `ScanState` holds a `SingleFlight` in place of the
  `AtomicBool` (`src-tauri/src/scan.rs:15-20`). `scan()` takes a guard with
  `try_start`. On `None` it returns, as it does today. It keeps the guard
  until the outcome is back. No swap or store of a flag stays in
  `src-tauri/src/scan.rs`. In `setup` (`src-tauri/src/lib.rs:45-56`) the
  shell calls `sweep_stale` one time, on `app_cache_dir()` if that resolves.
  These two shell edits have no test here. See Known weakness.

The fixture for AC1 and AC2 is a `tempfile::tempdir()` named scratch, made
new for each test, that holds:

- scan-old/selection.png and scan-older/display-1.png: two stale scans
  (the bytes can be anything);
- keep.txt, with the content `keep`;
- my-scan-keep/note.txt: a directory whose name contains `scan-` but does
  not start with it.

**AC1 — sweep_stale, run_scan and run_find_all remove the two stale scan directories of the fixture, and the two scans remove them before they capture.**
Instrument, three tests:
- `cargo:qr-core/scan::sweep_stale_removes_stale_scan_directories` calls
  `sweep_stale(scratch)` and asserts that scan-old and scan-older do not
  exist.
- `cargo:qr-core/scan::a_scan_sweeps_stale_scan_directories_before_it_captures`
  runs `run_scan` with `Permission(true)`, `RxingDecoder` and a Capturer
  fake. When the fake is called, it records whether scratch/scan-old or
  scratch/scan-older exists. Then it writes the code `https://example.com`
  to `dest`, as `Writes` does. The test asserts that the fake recorded
  neither, and that neither exists after the run.
- `cargo:qr-core/find_all::a_find_all_sweeps_stale_scan_directories_before_it_captures`
  does the same with `run_find_all` and a DisplaysCapturer fake. The fake
  records the same check, then writes one display with
  `https://example.com`.

Goes red when the sweep call is removed from the path that run_scan takes
before `temp_dir` (second test), or from run_find_all's path (third test).
Goes red when the sweep call moves to after the capture (second and third
tests: the fake saw scan-old). Goes red when the body of `sweep_stale` is
emptied (first test).

**AC2 — Paired with AC1: the sweep keeps keep.txt, my-scan-keep and the scan's own directory, and does not follow a scan-* link out of scratch.**
Instrument:
- The three AC1 tests also assert that keep.txt and my-scan-keep/note.txt
  still exist with their content.
- The two scan tests also assert that the outcome is
  `Found { codes }` with exactly one code, text `https://example.com`. This
  shows that the scan's own directory lived until the decode.
- `cargo:qr-core/scan::a_scan_named_link_does_not_lead_the_sweep_out_of_scratch`
  is a fourth test in `core/tests/scan.rs`, under `#[cfg(unix)]`. A second
  tempdir, outside, holds target.txt. In the fixture, scan-link is a
  symlink to outside (`std::os::unix::fs::symlink`). After
  `sweep_stale(scratch)`, outside/target.txt still exists. The test does
  not assert whether scan-link itself stays.

Goes red when `sweep_stale` removes each entry under scratch (keep.txt is
gone). Goes red when it matches the prefix with `contains` in place of
`starts_with`, or removes each directory (my-scan-keep is gone). Goes red
when the sweep runs after `temp_dir` made the scan's own directory: the fake
cannot write into the removed directory, so the test fails. Goes red when the
removal walks a `scan-*` entry itself and follows links, for example
`Path::is_dir` then `remove_file` on each child (target.txt is gone).

**AC3 — sweep_stale on a scratch path that does not exist returns without a panic.**
Instrument: `cargo:qr-core/scan::sweeping_a_missing_scratch_is_not_an_error`
calls `sweep_stale` on `tempdir().path().join("not-yet")`. The test passes
when the call returns. The startup sweep meets this case on the first launch:
the cache directory does not exist until a scan creates it
(`src-tauri/src/scan.rs:64`).
Goes red when `sweep_stale` unwraps or expects the result of reading
scratch, for example `fs::read_dir(scratch).unwrap()`.

**AC4 — SingleFlight refuses a second start while a guard lives, and frees the flag when the guard drops, also when the thread that holds the guard panics.**
Instrument: a new file single_flight.rs in core/tests, with three tests:
- `cargo:qr-core/single_flight::a_second_start_is_refused_while_a_guard_lives`:
  on `SingleFlight::default()`, the first `try_start` is `Some`. While that
  guard lives, a second `try_start` is `None`.
- `cargo:qr-core/single_flight::a_dropped_guard_frees_the_flight`: take a
  guard, drop it, and `try_start` is `Some` again.
- `cargo:qr-core/single_flight::a_guard_held_by_a_panicking_thread_frees_the_flight`:
  an `Arc<SingleFlight>`. A `std::thread::spawn` thread takes a guard with
  `try_start().expect(…)` and then calls `panic!("holder panicked")` while
  it holds the guard. `join` returns `Err`, and its payload downcasts to the
  `&str` `"holder panicked"`. This shows that the thread held the guard when
  it panicked, and did not fail at the `expect`. After that, `try_start` on
  the test thread is `Some`.

Goes red when the guard's Drop does nothing (second and third tests). Goes
red when Drop clears the flag only if `!std::thread::panicking()` (third
test). Goes red when `try_start` sets the flag with a plain `store(true)`
and returns `Some` without reading the flag first (first test).

## Known weakness of the instrument

- **The abnormal exits are not reproduced.** No test quits, crashes or
  SIGKILLs a process during a scan. The tests plant what such an exit leaves:
  `scan-*` directories with a screenshot in them. That such an exit leaves
  exactly this comes from reading the code and tauri's `exit`. Nobody has
  seen it on a Mac.
- **The shell's two edits have no instrument here.** These are the startup
  call in `src-tauri/src/lib.rs` and the use of SingleFlight in
  `src-tauri/src/scan.rs`. The shell does not build on this Linux box.
  `scripts/check-macos-shell.sh` compiles and lints it for macOS, but
  nothing runs it. The reviewer checks these edits by reading the diff;
  macOS CI builds them; a person on a Mac runs them (Human verification).
- **The sweep's safety depends on one scan at a time, and core cannot see
  that.** No qr-core test shows that the shell takes the guard before it
  calls run_scan. The sweep also assumes one app instance. The app has no
  single-instance plugin (`src-tauri/Cargo.toml` names none). A second
  instance started with `open -n` would sweep the first instance's live
  `scan-*` directory, and that scan would then fail or lose its screenshot.
  This story does not test or handle that case.
- **AC4 shows the guard clearing only on a panicking std thread.** In the
  shell, the guard lives in a tokio task. That tokio drops a panicked task's
  future, and with it the guard, comes from reading tokio 1.54.0
  (`poll_future`), not from a test. As stated under Evidence, no panic in
  today's code reaches that window.
- **AC4 does not race two threads.** A `try_start` written as a `load`
  followed by a `store`, in place of one atomic swap or compare-exchange,
  passes all three tests. The reviewer checks by reading that `try_start`
  is one atomic read-modify-write.
- **Not tested:** a stale directory that the sweep cannot remove (for
  example, because of permissions); a `scan-*` entry that is a regular file;
  symlinks other than the one in AC2.
- The tests run on Linux file systems. APFS and ~/Library/Caches are not
  exercised.

## Human verification

On a Mac, with a build from macOS CI. The cache directory is
~/Library/Caches/io.github.ilge-ustun.qr-desktop-scanner/.

- [ ] Startup sweep: with the app not running, put a directory scan-planted
      with any file in it, and a file keep.txt, in the cache directory.
      Launch the app and do not scan. scan-planted is gone. keep.txt stays.
      Any other directory that was there before (WebKit's, if there is one)
      stays.
- [ ] The defect's own case: start a drag scan. While the crosshair is up,
      `ls` the cache directory in Terminal: it shows one `scan-*` directory.
      End the app with `kill -9` (get the pid with `pgrep -f "QR Scanner.app"`),
      or with Quit in the tray menu if you can open the menu during a scan.
      If the crosshair is still up, press Esc. The `scan-*` directory is
      still there. Relaunch the app: the directory is gone.
- [ ] One scan at a time still holds: press the hotkey while the crosshair is
      up. No second crosshair comes. After Esc, the hotkey starts a new scan.
      After a drag scan ends, Find All Codes on Screen in the tray menu works.
- [ ] Do a drag scan that finds a code, a drag scan that you cancel with Esc,
      and a Find all. After them, the cache directory holds no `scan-*`
      directory.
