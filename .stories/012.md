# Story 012: The decoder stops pulling every image codec into the app: rxing loses its `image` feature, and qr-core decodes from the grey buffer

## Symptom

`core/Cargo.toml:9` asks for `image` with `default-features = false` and
only `png`. That request has no effect, because of the next line.
`core/Cargo.toml:10` gives rxing the `image` feature. In rxing 0.9.3 that
feature turns on two optional dependencies, `image` and `imageproc`.
rxing asks for `imageproc` without `default-features = false`.
imageproc 0.25.1's default features are `rayon` and `image/default`. Cargo
merges features: the build has one `image` package, so it gets image's
default formats too. These are avif (through ravif and rav1e), bmp, dds,
exr, ff, gif, hdr, ico, jpeg, png, pnm, qoi, tga, tiff and webp, plus rayon.

The lock shows it. The `image` entry (`Cargo.lock`, lines 2032-2053) depends
on exr, gif, image-webp, qoi, ravif, rayon, tiff and zune-jpeg. `imageproc`
(line 2066), `rav1e` (line 3502) and `ravif` (line 3537) are locked. The
`rxing` entry names `image` and `imageproc` (lines 3749-3750).

The app needs none of these codecs. It opens only PNG files it wrote itself:
`selection.png` (`core/src/scan.rs:73`) and `display-N.png`
(`src-tauri/src/platform/macos.rs:74`). It reads both with `image::open`
(`core/src/scan.rs:84`, `core/src/scan.rs:121`). In image 0.25.8,
`ImageReader::open` picks the decoder from the file's extension and does not
sniff the content. So only the PNG decoder is ever used to read a capture.

## Evidence

I read the code at `epic/quality` (a518b28). I built nothing and measured
nothing. The sizes below are the coordinator's, taken on develop.

### The coordinator's measurement (not repeated here)

A release binary of qr-core + `image::open` + decode went from 2,341,152 to
1,152,000 bytes (-51%) when rxing's `image` feature was dropped and the
decoder read the grey buffer. The dependency tree went from 319 to 158 lines.
Every qr-core test passed.

### The lock, checked in a scratch copy

I copied `Cargo.toml`, `Cargo.lock`, `core/` and `src-tauri/` to a temporary
directory and removed `"image"` from rxing's features there. Then I ran
`cargo metadata --offline --format-version 1`, which rewrites `Cargo.lock`
without building anything. This working tree was not touched.

- The lock went from 581 packages to 518. No package was added and no
  version changed. So the change needs no new crate and works offline.
- These leave: `imageproc`, `rav1e`, `ravif`, `exr`, `gif`, `image-webp`,
  `qoi`, `rayon`, `rayon-core`, `nalgebra` and their own dependencies.
- **These stay, and the criteria must not assert them gone:** `image`,
  `png`, `tiff` and `zune-jpeg`. The shell depends on
  `tauri-plugin-clipboard-manager` (`src-tauri/Cargo.toml:20`). That plugin
  depends on arboard 3.7.0 with its default features. Those include
  `image-data`, which turns on arboard's `image` dependency. On macOS that
  dependency asks for `image` with `tiff`, and on Linux and Windows with
  `png`. Tauri's `image-png` feature (`src-tauri/Cargo.toml:19`) asks for
  `png` too. `Cargo.lock` is one resolution for every target. So after this
  change, `image` in the lock depends on `bytemuck`, `byteorder-lite`,
  `moxcms`, `num-traits`, `png` and `tiff`, and `tiff` keeps `zune-jpeg`. On a
  Mac, the app still compiles image's TIFF decoder. That comes from the
  clipboard plugin, not from qr-core, and it is not part of this story.
- **imageproc, rav1e and ravif.** I checked who needs them. In the base lock
  only `rxing` depends on `imageproc`, only `ravif` on `rav1e`, and only
  `image` on `ravif`. Nothing in the shell (arboard, tauri, the plugins)
  needs any of the three once rxing stops asking. All three were gone from
  the scratch lock.
- **The qrcode dev-dependency** (`core/Cargo.toml:17`). The request says to
  leave it unless it alone keeps imageproc in the lock. It does not. qrcode
  0.14.1's `image` feature asks for `image` with `default-features = false`
  and no formats, and qrcode does not depend on imageproc. qrcode's own
  dev-dependency on `image` with its defaults is never resolved, because Cargo
  resolves dev-dependencies only for workspace members. In the scratch copy I
  also set `qrcode = "0.14"` with its default features. The lock still had no
  imageproc, rav1e or ravif. Leave `core/Cargo.toml:17` as it is.
- Build the lock with Cargo, not by hand: run `cargo metadata --offline
  --format-version 1 > /dev/null`, or any offline cargo command, from the
  repo root after editing `core/Cargo.toml`. Neither the baseline's `cargo`
  commands nor `scripts/check-macos-shell.sh` pass `--locked`. Cargo would
  quietly rewrite a lock that disagrees with the manifests, and nothing
  would fail.

### The decoder

- `detect` (`core/src/decode.rs:74-94`) builds the hints
  (`core/src/decode.rs:75-80`). It then copies the grey image into a
  `DynamicImage` (`core/src/decode.rs:81`) and calls
  `helpers::detect_multiple_in_image_with_hints`
  (`core/src/decode.rs:82-83`). `decode` calls `detect` up to three times: on
  the grey image, on the darkened image, and on the image enlarged three times
  (`core/src/decode.rs:35`, `core/src/decode.rs:43`,
  `core/src/decode.rs:54`). That makes up to three full copies per decode.
- In rxing 0.9.3, `detect_multiple_in_image_with_hints` exists only with
  rxing's `image` feature. Its `cfg` needs `image`, `multi_barcode_readers`
  and `decoders`. **So once the feature is dropped,
  `core/src/decode.rs:82-83` no longer compiles.** The baseline's
  `cargo clippy -p qr-core --all-targets` and `cargo test -p qr-core` fail
  until `detect` changes. That is what holds item 2 of the request. No
  criterion below has to.
- The replacement is `helpers::detect_multiple_in_luma_with_hints(luma:
  Vec<u8>, width: u32, height: u32, hints: &mut DecodeHints)`. Its `cfg`
  needs only `multi_barcode_readers` and `decoders`, so it stays available.
  Its body matches the image helper line for line, apart from the source:
  - Both use a `GenericMultipleBarcodeReader` around a
    `MultiUseMultiFormatReader` and a `HybridBinarizer`.
  - Both set `TryHarder` to true when it is unset.
  - The luma helper wraps the bytes in
    `Luma8LuminanceSource::new(luma, width, height)`.
  - The image helper uses `BufferedImageLuminanceSource::new(img)`. For a
    `DynamicImage::ImageLuma8`, that takes the grey buffer as it is and
    wraps it in the same `Luma8LuminanceSource`.

  So the pixels, the binarizer and the reader are the same.
- **The one difference.** `BufferedImageLuminanceSource` supports a 45°
  rotation, which it does with imageproc. `Luma8LuminanceSource` returns an
  error for it. In rxing 0.9.3 no reader asks a source for a 45° rotation.
  The readers that rotate, the 1D ones, rotate by 90°, and both sources
  support that. The hints restrict decoding to QR anyway. So the two paths
  should find the same codes in the same order. I read this in the source.
  I have not observed it beyond the fixtures.
- The luma helper returns an error for a zero width or height.
  `unwrap_or_default()` turns that into no codes, as the current code does.
- **What stays the same.** These must not change:
  - the hints: `QR_CODE` only, `TryHarder`, `AlsoInverted`;
  - the order of the three passes and the 600-pixel rule;
  - the de-duplication by text, keeping first occurrences in rxing's order
    (`core/src/decode.rs:85-93`);
  - the `Decoder` trait, which keeps `&DynamicImage`
    (`core/src/decode.rs:19`).

  `core/tests/find_all.rs:90` implements that trait, and
  `core/src/scan.rs:88` calls it. `DynamicImage` comes from qr-core's own
  `image` dependency, so it is unaffected.
- **Copies.** The helper takes the bytes by value. `decode` still needs
  `gray` after the first pass, so that pass needs one copy. The darkened and
  enlarged images are not used after their pass. They can be moved in with
  `into_raw()`, without a copy. rxing also exports a borrowing source,
  `Luma8Source::new_with_slice`. With it and the reader types, no pass would
  copy, but I have not tried it. How many copies are made is the builder's
  choice, and no test reads it.
- The fixtures (`core/tests/common/mod.rs:9-40`) are drawn at test time with
  qrcode. These tests run in the baseline and must pass unchanged:
  - `core/tests/decode.rs:17-87`: a plain code, a code in a larger
    screenshot, a rotated code, a small code, a code with seams, a
    light-on-dark code, two codes, the same code twice, and no code;
  - `core/tests/scan.rs`;
  - `core/tests/find_all.rs`.

  `core/tests/*` is denied, so they cannot be edited to pass.

### Writing the test

- The fleet's only instrument is vitest. Rust is a gate, not an instrument.
  vitest collects only `src/**/*.test.{ts,tsx}` (`vite.config.ts:12`). So
  the new test has to live under `src/`. **This differs from the request,
  which lists `src/**` as out of scope.** As in stories 008 and 009,
  `scope_deny` names the product code and every existing test. It leaves room
  for one new `.ts` test under `src/__tests__/`, for example
  `src/__tests__/coreDependencies.test.ts`. `src/__tests__/*.tsx` is denied.
- Existing tests read config files as text with Vite's `?raw`
  (`src/__tests__/ciConfig.test.ts:7-9`). `tsconfig.json:14` types `?raw`
  through `vite/client`. `@types/node` is not installed, so a `node:fs`
  import would fail `tsc`. Nobody has tried `?raw` on `core/Cargo.toml` or
  `Cargo.lock` yet (not observed).
- No TOML parser is installed, and `package.json` and `package-lock.json`
  are denied. The test reads both files with the small line rules given
  under each criterion.

## Acceptance criteria

The instrument for both criteria is one new vitest `.ts` file under
`src/__tests__/`. It imports `core/Cargo.toml` and `Cargo.lock` with
`?raw`.

**AC1 — In `core/Cargo.toml`, rxing's features are exactly `qrcode`, `decoders`, `multi_barcode_readers` and `encoding_rs` with `default-features = false`, and `image` keeps `default-features = false` with only `png`.**
Instrument: the test reads `core/Cargo.toml`.
- The dependencies table is the lines after the line `[dependencies]`, up to
  the next line that starts with `[`.
- In that table, exactly one line matches `^rxing\s*=`, and exactly one
  matches `^image\s*=`. A line starting `imageproc` does not match.
- Each of those two lines contains `default-features = false` and one
  `features = [ … ]` on the same line. The features are the double-quoted
  strings inside the brackets.
- rxing's features, as a set, are exactly `qrcode`, `decoders`,
  `multi_barcode_readers` and `encoding_rs`. image's features are exactly
  `png`.
- The test fails if it cannot find a line or its feature list. That includes
  a dependency rewritten as a `[dependencies.rxing]` table or spread over
  several lines.

Fails on the base: `core/Cargo.toml:10` lists `"image"`.
Goes red when:
- `"image"` is put back in rxing's features at `core/Cargo.toml:10`;
- `"encoding_rs"` is dropped from rxing's features;
- `default-features = false` is removed from the rxing line. rxing 0.9.3's
  default features include `image`, so this re-adds it. Cargo cannot
  re-resolve that offline here: rxing's other defaults need crates that are
  not in the local registry (observed). So only this criterion catches it;
- image's features become `["png", "jpeg"]`;
- `default-features = false` is removed from the image line.

**AC2 — Paired with AC1: `Cargo.lock` has no package named `imageproc`, `rav1e` or `ravif`, and the `rxing` package depends on neither `image` nor `imageproc`.**
Instrument: the test reads `Cargo.lock`.
- A package is the text from a `[[package]]` line to the next `[[package]]`
  line, or to the end of the file.
- Its name is the quoted value of its `name = "…"` line.
- Its dependencies are the quoted strings in its `dependencies = [ … ]`
  block. Each is compared on the part before the first space, because Cargo
  writes `"thiserror 2.0.21"` when two versions are locked.
- **Sanity checks**, so that the test cannot pass on a file it failed to
  read: the lock has more than 100 packages, exactly one named `rxing` and
  one named `qr-core`, and `qr-core`'s dependencies include `rxing` and
  `image`.
- No package is named `imageproc`, `rav1e` or `ravif`. The names must match
  exactly: `image-webp` is not `image`.
- `rxing`'s dependencies contain neither `image` nor `imageproc`.

Fails on the base: `imageproc`, `rav1e` and `ravif` are locked, and rxing's
entry names `image` and `imageproc`.
Goes red when:
- `Cargo.lock` is restored from `epic/quality` and `core/Cargo.toml` keeps
  the change. AC1 stays green, and this is the mutation only AC2 catches;
- `"image"` is put back in rxing's features and the lock is rebuilt with
  `cargo metadata --offline --format-version 1`. All three come back
  (observed in the scratch copy);
- `core/Cargo.toml:9` becomes `image = "0.25"`, with image's default
  features, and the lock is rebuilt the same way. `ravif` and `rav1e` come
  back through image's `avif`, but `imageproc` does not (observed). This is
  why the criterion names `rav1e` and `ravif`, not just `imageproc`;
- `imageproc = "0.25"` is added to `[dependencies]` in `core/Cargo.toml` and
  the lock is rebuilt. All three come back (observed). AC1 stays green,
  because it looks only at the `rxing` and `image` lines.

The criterion leaves out `tiff` and `zune-jpeg`, because the clipboard
plugin keeps them (see Evidence). It also leaves out `exr`, `gif`,
`image-webp`, `qoi` and `rayon`. They leave the lock too, but the three it
names are enough to catch rxing's feature and image's default formats coming
back.

## Known weakness of the instrument

- **Binary size is not asserted by any test.** The -51% is the coordinator's
  measurement of a small qr-core binary on develop. It is not a measurement
  of the app. On a Mac, image also keeps its TIFF decoder through arboard,
  so the app's saving is smaller than the qr-core figure. By how much was
  not measured.
- **Text only.** The criteria read two files as text. They prove the
  manifest and the committed lock say rxing no longer pulls in image or
  imageproc. They do not prove the committed lock is the one Cargo would
  resolve. The baseline's `cargo` commands do not pass `--locked`, so a
  hand-edited lock that Cargo disagrees with is rewritten in the reviewer's
  tree, and nothing fails. Human verification below checks this once.
- **The line reader is not a TOML parser.** It requires each of the two
  dependencies written inline on one line. A valid rewrite into table form
  fails the test, which fails closed rather than passing.
- **Decoding behaviour is held by the cargo fixtures in the baseline, not by
  a criterion.** `cargo test -p qr-core` runs the tests in
  `core/tests/decode.rs`, `core/tests/scan.rs` and `core/tests/find_all.rs`.
  Their codes are drawn by qrcode: clean, grey, with sharp edges.
  Screenshots from a real Mac are different: Retina scale, antialiasing,
  colour converted to grey. On a Mac only a person checks them. The claim
  that the luma path and the image path see the same pixels comes from
  reading rxing 0.9.3. It was not observed beyond those fixtures.
- **Copies are not tested.** Nothing checks how many copies `decode` makes.
- **Other codecs.** A change that brings back only `exr`, `gif`,
  `image-webp`, `qoi` or `rayon` is caught only if it is made on qr-core's
  `image` line (AC1). An example is image's features becoming
  `["png", "gif"]`. Made anywhere else, it is not caught.
