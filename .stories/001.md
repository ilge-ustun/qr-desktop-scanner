# Story 001: Contact codes (vCard, MECARD) get their own card

## Symptom

Only Wi-Fi codes get a card of their own; a contact code gets none.
`classify` (`src/lib/payload.ts:33-54`) knows `mailto:`, `tel:` and `WIFI:`. Anything else with a scheme and no
whitespace is a link (`src/lib/payload.ts:50-52`), and the rest is text
(`src/lib/payload.ts:53`). Reading the current files (nothing was run):

- **vCard** (`BEGIN:VCARD` … `END:VCARD`) has line breaks, so it gets the text
  card. The whole vCard is printed as one `.content` block
  (`src/components/ResultCard.tsx:63`) and its one Copy copies all of it
  (`src/components/ResultCard.tsx:79-81`).
- **MECARD** gets the text card if it contains a space. Without a space,
  `MECARD:…` parses as a URL, so it gets a *Link* card: "Link · check before
  opening", the app-scheme warning (`src/lib/urlSafety.ts:57-64`), no
  headline and no Open.

Phone, SMS and geo codes are story 002, cut from this story's first draft and
written once this one is on `epic/cards`.

## Evidence

- **Where the new branch goes.** A MECARD with no space parses as a URL, so
  today it is a Link card (checked with node: `URL.canParse` is true for F3).
  The contact branches in `classify` therefore go before the link branch at
  `src/lib/payload.ts:50-52`. The link tests at
  `src/__tests__/payload.test.ts:10-17` stay as they are.
- **The pattern to follow is Wi-Fi.** `classify` attaches the `parseWifi`
  result (`src/lib/payload.ts:41-43`). `parseWifi` returns null without a
  network name (`src/lib/payload.ts:89-90`). `ResultCard` sends a code to
  `WifiCard` only when it parsed (`src/components/ResultCard.tsx:21-23`). In
  `WifiCard`, the network name is in `.headline`
  (`src/components/WifiCard.tsx:52`) and the password is in `.mono`
  (`src/components/WifiCard.tsx:58`). Its Copy copies only the password
  (`src/components/WifiCard.tsx:66-75`). An open network has no password row
  (`src/components/WifiCard.tsx:56-63`).
- **Type.** `.headline`, `.mono` and `.content` set Sometype Mono
  (`src/styles.css:316-338`). `button` and `.meta` set Silkscreen
  (`src/styles.css:73-82`, `src/styles.css:289-294`).
- **How this story reads the human's decisions.**
  1. **Fields.** "Phone numbers, email addresses, organisation, website" is
     the complete list: TEL, EMAIL, ORG and URL. ADR, TITLE, NOTE, BDAY and
     NICKNAME are not shown. Coordinator's choice, under the human's
     delegation: the list as asked; more fields can be a later story.
  2. A contact **parses** when:
     - a vCard starts with `BEGIN:VCARD`, has an `END:VCARD` line, and has a
       non-empty FN, or a non-empty N when there is no FN;
     - a MECARD has a non-empty N.

     These are the fields each format requires: FN in vCard 3.0/4.0, N in
     MECARD. This matches `parseWifi`, which returns null without a network
     name.
  3. **The name.**
     - The vCard FN is shown as written.
     - Without an FN, the vCard N `Family;Given;…` is shown as `Given Family`.
     - The MECARD N `Last,First` is shown as `First Last`.

     N components are split on unescaped `;` in vCard and on unescaped `,` in
     MECARD.
  4. The contact card has no Copy for the whole raw code. Nobody asked for one.
     The builder decides whether the contact's name gets its own Copy.
- **Format rules used.**
  - vCard (RFC 6350):
    - A line break (CRLF or LF) followed by one space or tab continues the
      previous line. Drop the break and that one character.
    - Unescape `\\`, `\,`, `\;` and `\n` (also `\N`).
    - Property names are case-insensitive.
    - Drop a group prefix (`item1.`) and parameters (`;TYPE=…`).
    - I remember Apple Contacts putting URLs in groups, but I have not checked
      it here.
  - MECARD: escapes work as in `parseWifi`, where a backslash before any
    character gives that character. A field ends at an unescaped `;`. Only
    the first `:` separates the field name, so `URL:https://…` keeps its
    colon.
- The label for the new kind (`LABELS`, `src/lib/payload.ts:19-25`) is up to
  the builder. It is the app's own words, so Silkscreen is right for it.

## Acceptance criteria

The criteria range over these inputs and nothing else. They are written as
TypeScript, so the strings are exact. The builder can paste them into the
tests.

```ts
// Contacts
const V1 =
  "BEGIN:VCARD\r\n" +
  "VERSION:3.0\r\n" +
  "N:Doe;Jane;;;\r\n" +
  "FN:Jane Doe\r\n" +
  "ORG:Smith\\, Jones\\; Partners\\\\Legal\r\n" +
  "TEL;TYPE=CELL:+31 6 1234 5678\r\n" +
  "TEL;TYPE=WORK,VOICE:+31 20 123 4567\r\n" +
  "EMAIL;TYPE=INTERNET:jane@example.com\r\n" +
  "EMAIL:j.doe@example.org\r\n" +
  "item1.URL;type=pref:https://example.com/\r\n" +
  " jane\r\n" + // folded: continues the URL line
  "END:VCARD";
const V2 = "BEGIN:VCARD\nVERSION:4.0\nN:Doe;Jane;;;\nORG:Acme\\nLabs\nTEL:+31201234567\nEND:VCARD";
const M1 =
  "MECARD:N:Doe,Jane;TEL:+31612345678;TEL:+31201234567;EMAIL:jane@example.com;" +
  "ORG:Smith\\, Jones\\; Partners\\\\Legal\\: NL;URL:https://example.com/jane;;";
// Contacts that do not parse
const F1 = "BEGIN:VCARD\nVERSION:3.0\nFN:Jane Doe\nTEL:+31201234567"; // no END:VCARD
const F2 = "BEGIN:VCARD\nVERSION:3.0\nTEL:+31201234567\nEND:VCARD"; // no FN, no N
const F3 = "MECARD:TEL:+31201234567;EMAIL:jane@example.com;;"; // no N
// Markup
const H1 = "BEGIN:VCARD\nFN:<img src=x onerror=alert(1)>\nTEL:<b>+31</b>\nEND:VCARD";
```

- **Kind name.** The new payload kind is `"contact"`. Field names are the
  builder's.
- **Card tests.** They render `ResultCard` with `vi.fn` callbacks, as the
  existing helper does (`src/__tests__/ResultCard.test.tsx:8-23`). That way
  `classify`, the routing and the card are all exercised.
- **"The buttons are …"** means the full list of `button` elements in the
  document.
- **"A Copy button"** is a button whose accessible name starts with `Copy`.

**AC1 — classify reads the named vCard and MECARD codes (V1, V2, M1) into a contact with the named fields.**
Instrument: a test in `src/__tests__/payload.test.ts`. It asserts that
`classify` returns kind `"contact"` with these fields:

- **V1:**
  - name `Jane Doe`
  - phones `+31 6 1234 5678` then `+31 20 123 4567`
  - emails `jane@example.com` then `j.doe@example.org`
  - organisation `Smith, Jones; Partners\Legal`
  - website `https://example.com/jane`: the fold is joined, and the `item1.`
    group and `;type=pref` are dropped.
- **V2:**
  - name `Jane Doe`, taken from N because there is no FN
  - phone `+31201234567`
  - organisation `Acme`, a newline, then `Labs`
- **M1:**
  - name `Jane Doe`
  - phones `+31612345678` then `+31201234567`
  - email `jane@example.com`
  - organisation `Smith, Jones; Partners\Legal: NL`
  - website `https://example.com/jane`

Goes red when any of these changes is made:

  website becomes `https://example.com/`.
- The `\,` rule is dropped from vCard unescaping. V1's organisation keeps a
  backslash.
- The vCard branch is removed from `classify` in `src/lib/payload.ts`. V1
  comes back kind `"text"`.

**AC2 — paired with AC1: the named contact codes that do not parse (F1, F2, F3) get the existing text card.**

**AC3 — the contact cards for V1 and M1 copy each listed value with its own button and offer nothing else.**

**AC4 — on the cards for V1, M1 and H1, decoded text is mono text and never a button, a label, a link or markup.**
Instrument: a test in `src/__tests__/ResultCard.test.tsx` that renders each
code and checks the following.

These are the values checked:
- V1 and M1: the name, phones, emails, organisation and website from AC1.

For each value:
- At least one element's own text equals it exactly. Find these with
  testing-library's `getAllByText`.
- Each such element has class `headline`, `mono` or `content` itself.
- None of them is inside a `button` or `.meta`: `closest("button, .meta")`
  is null.
- No `button` element and no `.meta` element has that value in its
  `textContent`.

On these cards, the document has no `a` element.

For H1:
- The document has no `img` and no `b` element.
- Some element's text contains `<img src=x onerror=alert(1)>`.

Goes red when any of these changes is made:
- A card renders a value through `dangerouslySetInnerHTML`. H1 then creates
  an `img`.
- A value is put in a button's label (`Copy +31 6 1234 5678`) or in the
  `.meta` label.
- An email or phone is rendered as a `mailto:` or `tel:` anchor, or the
  website as an `a`.
- A value's element gets a class other than the three. The Sometype Mono rule
  is on those three classes (`src/styles.css:316-338`).

## Known weakness of the instrument

- **Fonts are not seen.** jsdom loads no stylesheet and does no layout. AC4
  proves which class holds each value, and that no value sits in a button or
  `.meta`. It does not prove that the glyphs on screen are Sometype Mono. A
  new CSS rule that sets `var(--pixel)` on `.mono` inside a new card would
  pass. The reviewer should read the `src/styles.css` diff, and a person
  should look.
- **Placement of Copy buttons is not seen.** The Copy tests click every Copy
  button and collect what `onCopy` received. They do not show which value a
  button sits next to. They do not show that "Copied" appears only on the
  button that was clicked.
- **The callbacks are mocks.** `onCopy` and `onOpen` are `vi.fn`; the
  clipboard never runs.
- **Parsers are proven on the named inputs only.** These cases are not
  specified:
  - vCard 2.1 QUOTED-PRINTABLE and CHARSET, base64 PHOTO, or several vCards in
    one code;
  - parameters with quoted colons, or N and ORG components beyond the named
    inputs;
  - MECARD fields other than N, TEL, EMAIL, ORG and URL.

  Odd output on any of the
  unspecified cases is a gap in the spec, not a failure of these criteria.
- **No real code was scanned.** The inputs were written from the format
  specifications (RFC 6350, DoCoMo MECARD). None was
  captured from a generator or a phone. Apple's `item1.` grouping comes from
  memory.
- **Base behaviour.** The Link-card outcome for a MECARD without a space was
  checked with node's `URL.canParse`; the rest of Symptom comes from reading
  the code.

## Human verification

On a Mac, with the build from macOS CI:

- [ ] Export a contact from Contacts as a vCard, make a QR code of it and scan
      it. The name is the headline, and the phones, emails, organisation and
      website are listed, each with a Copy. Paste each one into TextEdit: you
      get only that value.
- [ ] Do the same with a MECARD from an online generator.
- [ ] No contact card has a Call, Email, Open or Add to Contacts button.
- [ ] Decoded text shows lower case (Sometype Mono). Labels and buttons are
      Silkscreen. Corners are square, and only the two inks are used.
- [ ] "Copied" appears on the clicked button only, then goes back to "Copy".
- [ ] A long email or organisation wraps inside the card, and the popover
      grows and scrolls as before.
